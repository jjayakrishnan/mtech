Probabilistic language models

Formally, a language model assigns a probability to a sequence of words, and — more usefully — a probability distribution over what word comes next, given what came before:

$$ P(w_t \mid w_1, w_2, \ldots, w_{t-1}) $$
Analogy — predicting the next scene in a franchise If you've watched every Marvel movie in order, you can predict with decent confidence what kind of scene comes after a big battle (a quiet aftermath scene, usually) — not because you memorised a rule, but because you've absorbed the pattern from dozens of examples. A language model does the same thing with text: having "read" huge amounts of it, it estimates how likely each possible next word is, given everything written so far.

The handout's three-step history of how we estimate that probability maps directly onto Session 1's "LLM landscape" section:

  • N-gram models — count how often each word follows the previous (N-1) words in a huge corpus, directly from frequency tables. Simple, fast, and badly limited: it only ever "sees" the last N-1 words, so it has the exact same long-range memory problem described in the Prerequisites Primer.
  • Neural language models (feed-forward nets) — replace the frequency table with a small neural network that learns a continuous representation of context, introducing learned word representations (an early form of embeddings) instead of raw counts.
  • Transformer-based LLMs — today's models, where attention replaces the fixed N-1-word window with a mechanism that can look arbitrarily far back (see the Prerequisites Primer).

The building blocks, end to end

Before any architecture detail, Session 1 lays out the full pipeline a sentence travels through — this exact sequence is what the rest of the course spends 15 sessions unpacking one stage at a time.

Memorise — the pipeline Raw text → Tokenizer (BPE) → token IDs → Token embedding lookup → add positional encoding → stack of Transformer blocks (attention + feed-forward) → Language modelling head → probability distribution over the whole vocabulary → a decoding strategy picks the next token → append it and repeat (autoregressive loop).

Tokenization & BPE, worked example

The Prerequisites Primer introduced BPE as "LEGO bricks instead of pre-built statues." Here's the actual algorithm, worked through on a toy corpus — exactly the kind of fully-solved example this course rewards in exams.

Worked exampleBPE on the toy corpus: "low", "lower", "lowest", "newer", "wider" (with frequencies 5, 2, 2, 6, 3)

Step 0 — start from characters, each word ending with an end-of-word marker _: l o w _ (×5), l o w e r _ (×2), l o w e s t _ (×2), n e w e r _ (×6), w i d e r _ (×3).

Step 1 — count every adjacent symbol pair across the whole weighted corpus. The pair (e, r) appears in "lower" (×2), "newer" (×6), and "wider" (×3) = 11 times, the most frequent pair. Merge it: e r → er.

Step 2 — recount. Now (er, _) appears 2+6+3 = 11 times (every word that just got an "er" immediately ends). Merge it: er + _ → er_.

Step 3 — recount again. (n, e) appears in "newer" ×6 — but check (l, o): it appears in "low" (×5), "lower" (×2), "lowest" (×2) = 9 times, now the winner. Merge l o → lo.

…and so on, a fixed number of merges (or until a target vocabulary size is reached). Notice what falls out for free: "lower" and "newer" end up sharing the learned sub-word er_, and "low", "lower", "lowest" end up sharing lo — the algorithm discovers morphology (word-forming patterns) purely from frequency, with nobody hand-coding "-er is a comparative suffix."

Byte-level BPE (what GPT-style tokenizers actually use) runs this same merge process starting from raw UTF-8 bytes instead of Unicode characters. The payoff: with only 256 possible starting symbols (every byte value), there is no such thing as an "unknown token" — any string in any language, emoji included, can always be represented, just possibly as more, smaller tokens for rare scripts.

Token embeddings + positional encoding

Each token ID is looked up in a learned embedding table to get a vector (the "meaning" vector from the Prerequisites Primer), and a separate positional-encoding vector is added on top — literally summed, element-wise — before anything enters the Transformer stack. From the recording: "you have tokens… the embedding — that is, meaning vector plus the positional encoding vector — we pass it as input to the LLM."

Where embeddings reappear laterNot just inside the model

Session 1 also flags that embedding models (OpenAI's embedding API, or a BERT model with its classification head removed) are a separate, lightweight tool you'll use directly — e.g. for retrieval (RAG, Session 12) — distinct from the embeddings learned inside a generative LLM. As the professor puts it, a small, dedicated embedding model "is very lightweight" and often the right choice for a retrieval system, rather than running a full LLM just to get a vector.

The language modelling head

After the Transformer stack has processed a sequence, the final hidden state is projected by one more learned linear layer — the language modelling head — into a vector the size of the entire vocabulary (tens of thousands of numbers, one per possible token), then turned into probabilities with softmax. Whichever decoding strategy you pick (covered properly in Session 5 — greedy, top-k, top-p, temperature) chooses the actual next token from that distribution, the token is appended to the sequence, and the whole pipeline runs again for the token after that. This loop — one forward pass per generated token — is autoregressive generation, and it's the reason LLMs "type" their answers out rather than producing the whole response at once.

Self-check

Q1. Why does an n-gram language model struggle with long sentences, in exactly the same way an RNN does?
An n-gram model only ever conditions its next-word probability on the previous N-1 words — anything further back is invisible to it by construction, the same fixed-window blind spot that limits RNN "memory" in practice (even though RNNs theoretically see the whole sequence, their compressed hidden state degrades over distance). Both approaches cap how far back useful context can reach; attention in a Transformer removes that cap entirely.
Q2. In the BPE worked example, why did "lower" and "newer" end up sharing the sub-word token "er_" after just two merges?
Because "er" followed immediately by the end-of-word marker was the single most frequent adjacent pair across the weighted corpus (11 occurrences, from "lower"×2 + "newer"×6 + "wider"×3), so BPE's frequency-first merge rule picked it early. This is the algorithm discovering a shared suffix pattern purely from co-occurrence counts, without any hand-coded linguistic rule.
Q3. What's added to a token embedding before it enters the Transformer stack, and why is it necessary?
A positional encoding vector is added, element-wise, to the token's embedding. It's necessary because attention itself has no built-in sense of word order — without positional information, "the model" and "model the" would look identical to the attention mechanism, since it compares token pairs regardless of their position in the sequence.
