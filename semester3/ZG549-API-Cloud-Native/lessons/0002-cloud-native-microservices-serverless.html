Modern application requirements

The whole idea: apps like Netflix, Instagram or Flipkart serve millions at once, never go down, and ship updates constantly — traditional architecture can't keep up.

Platform → what it must handle
Platform typeExampleKey demand
Streaming / OTTNetflix, Prime Video, HotstarMillions of simultaneous users: authentication, recommendations, playback. Needs high availability, low latency, scalability (buffering = delivery problem)
Social mediaInstagram, Facebook, XSudden spikes (celebrity post → millions react); store enormous content and retrieve it fast
E-commerceFlipkart, AmazonBrowse, inventory, cart, orders, payments, shipping; traffic spikes in sales — if payments fail users can't buy, so separate responsibilities
Data delugeInternet-scale activityHuge, constantly growing data; needs efficient processing and reliable data management

General requirements (4)

  1. Zero downtime — stay available even during updates. Techniques: redundant instances, load balancers, rolling deployments. No absolute guarantee — it is a design objective.
  2. Shortened feedback cycles — release often (not every few months) so problems are found early and customer needs met quickly (automated build/deploy).
  3. Mobile and multi-device support — web, phone, tablet, laptop; APIs let many front-ends share the same back-end.
  4. Data-driven — use collected data for decisions (Netflix/e-commerce recommendations from viewing and purchase history).

Four shifts that led to cloud native

#FromToWhy it matters
1MonolithMicroservicesOne deployable unit → separate services you can update and scale independently
2On-premisesCloudStop buying/maintaining servers; rent capacity and managed services on demand (AWS, Azure, GCP)
3Virtual machinesContainersA VM carries its own guest OS (starts in minutes); containers share the host OS (lighter, start in seconds)
4Traditional CI/CDCloud-native CI/CDOne pipeline for everything → one independent pipeline per service (rebuild only what changed)

Evolution in four dimensions: process Waterfall → Agile → DevOps; architecture Monolith → N-tier (presentation/business/data) → Microservices; servers Physical → VMs → Containers; infrastructure Data centre → Hosted → Cloud. Cloud native = Agile + DevOps + microservices + containers + cloud, taken together as one engineering approach.

Cloud-enabled vs cloud-based vs cloud-native

Analogy — three ways to move into a new city Cloud-enabled: keep living in your old house but rent a storage unit in the city. Cloud-based: pick up your whole old house and set it down in the city — same layout, new address. Cloud-native: design a new house built for the city — modular rooms you can expand one at a time.
Cloud-enabledCloud-basedCloud-native
What it isExisting/legacy app that uses some cloud servicesExisting app moved to cloud infrastructure, unchanged ("lift and shift")App designed to exploit the cloud
Typical architectureLegacyUsually monolithicMicroservices
ScalabilityLimitedDepends on app design (monolith → limited)Flexible, per service
DeploymentTraditional / hybridCloud deploymentAutomated CI/CD, containerised
ExampleBank app on a mainframe calling cloud-hosted account APIs; on-prem app storing images in S3 or sending cloud notificationsMonolithic e-commerce app moved from own servers to EC2 / Azure VMsE-commerce split into product, payment, user, order, cart, notification services on Docker + Kubernetes
PricingMostly existing (on-prem) costs plus the cloud services usedPay-as-you-goConsumption-based (e.g. serverless charges per request/resource used) — but not always cheaper: clusters and microservices have operating cost

Cloud-based benefits: no hardware to manage, scale up/down, auto-scaling, high availability (e.g. 99.99%), pay for what you use. Q&A clarification: in cloud-based, the hardware is managed by the provider and auto-scaling is available — but because the app inside is a monolith, how well it scales still depends on the application design.

Don't mix upMicroservices ≠ cloud

Microservices can run on-prem, and a monolith can run in the cloud. The two choices are independent: architecture style (monolith/microservices) vs where it runs (on-prem/cloud).

The cloud-native stack (bottom → top)

┌────────────────────────────────────────────┐ │ DevOps / CI-CD ← automated build, test, release │ ├────────────────────────────────────────────┤ │ Microservices ← small business capabilities │ ├────────────────────────────────────────────┤ │ Containers ← app + dependencies packaged │ ├────────────────────────────────────────────┤ │ Cloud infrastructure ← compute, storage, services │ └────────────────────────────────────────────┘

Cloud-native vs cloud-based — three areas

  • Design: cloud-native plans for failure because it is distributed (many services, network, databases). Tools: retries, timeouts, redundant instances, circuit breakers (stop repeatedly calling a failing service to avoid cascading failures).
  • Implementation: containers + automated pipelines. Instead of manually installing dependencies, ship a container image. Cloud-based apps migrate without redesign but still need configuration/software setup, so they're slower to deploy.
  • Pricing: described above. No approach is guaranteed cheaper.

Case studies — what went wrong, what went right

Flipkart Big Billion Day — why scaling alone was not enough

The sale opened at midnight with discounts across 70+ categories and flash sales. Millions hit the same products at once: product page → inventory → order → payment. The site crashed; carts emptied; items showed "sold out" after recovery; some customers were charged with no order.

ProblemWhat happenedFix
Insufficient capacityServers built for ~10,000 concurrent requests suddenly saw 100,000Add instances + load balancer; capacity planning and performance testing
Database bottleneckThousands buy the same product; uncoordinated inventory updates show wrong stockTransactions, concurrency control, inventory reservation
Cart inconsistencyCart held only in one server's memory; server fails → cart goneStore session/cart outside the app server so it survives across instances
Distributed transactionPayment succeeded but order service was down → money taken, no orderIdempotency keys, durable event queues, compensating transactions

Worked exampleIdempotency key: no double charge

Idempotent = repeating the operation produces no extra effect.

Step 1. Client sends POST /pay with key K=order-123-pay, amount ₹500. Server charges ₹500 and stores K → success.

Step 2. The order service was down, the client times out and retries the same request with the same key.

Step 3. Server sees K already exists → returns the stored result and does not charge again. Total charged = ₹500, not ₹1000.

Lesson from the lecture: scaling is not enough — services and databases need reliable coordination.

Hotstar — 25 million concurrent users

(The professor asked the class what Hotstar must have done; answers: predict traffic and stress-test, auto-scale, monitor.) The full set:

  1. CDN (content delivery network) — serve content from servers geographically close to users, shielding the origin.
  2. Load balancing — spread requests across many instances.
  3. Auto-scaling — add capacity when a major sports event ramps traffic (and remove it afterwards).
  4. Caching — keep frequently requested data to avoid repeated database work.
  5. Monitoring — latency, error rate, CPU utilisation, throughput.
  6. Adaptive bit-rate streaming — video quality adjusts to each viewer's network, reducing buffering.

Flipkart vs HotstarThe contrast to remember

Hotstar predicted the spike and prepared (CDN, auto-scaling, load balancing, caching, observability) before it arrived. Flipkart's failure was capacity, database, cart and payment-coordination design.

Amazon Prime Video — when going back to a monolith wins

A video-monitoring workload built as distributed microservices was consolidated into a single process hosted on ECS, cutting operational cost by ~90%. Why microservices cost so much here: every call between services crosses the network, with communication overhead, serialisation, extra infrastructure and operational complexity. Components that run together exchange data in memory instead of via remote calls.

Memorise — the moral Choose the architecture from the requirements. A monolith can be simpler, faster and cheaper; microservices are not always better.

Monolith vs microservices

Monolith

All modules (e.g. in a food-delivery app: customer, restaurant, menu, order, payment, delivery tracking) are packaged and deployed as one unit. Modules call each other directly inside the app. Easy to build, test and deploy while small. But modules share a deployment boundary — fixing one bug means rebuilding, testing and redeploying everything.

Monolith limitationMeaning
Technology barrierStarted in Java and now want Python for ML? Hard — same runtime, tightly integrated
ScalabilitySearch gets far more traffic than registration, yet you must scale the whole application (wasted resources)
ComplexityThousands of classes and dependencies — hard to know what a change affects
Difficult maintenanceNew developers must learn a lot; changing shared code breaks unrelated features

Microservices — four properties

  1. Autonomous — each service controls its own implementation and operation.
  2. Loosely coupled — talk through well-defined interfaces; minimal dependencies.
  3. Independently deployable — release one service without the whole app.
  4. Business-domain oriented — one service per business capability. This follows the Single Responsibility Principle (the "S" of SOLID): group things that change for the same reason, separate things that change for different reasons (restaurant rules vs payment rules).

Why use them: independent scaling, faster releases (deploy a new recommendation algorithm alone), fault isolation (recommendation service down, rest keeps working). Costs: network communication, data consistency, extra infrastructure, operational complexity. Worth it when independent development and scaling matter.

Worked exampleWhy independent scaling saves resources (designed example)

Assume a shop has 5 modules (search, users, cart, orders, payments). One copy of each module handles 1,000 requests/s. Search suddenly needs 5,000 req/s; the other four need 1,000 each.

Monolith: must run 5 copies of the whole app → \( 5 \times 5 = 25 \) module-copies.

Microservices: search ×5 + four others ×1 → \( 5 + 4 = 9 \) module-copies.

Saving: \( (25-9)/25 = 64\% \) fewer resources. Try other numbers below.

Service decomposition, API gateway, and API-first design

Client app ──► API Gateway (single entry point, routes requests) ├──► Customer service ─ own DB ├──► Restaurant service ─ own DB ├──► Order service ─ own DB ├──► Payment service ─ own DB └──► Kitchen service ─ own DB (services talk via APIs or asynchronous messaging)

API-first design: define the interface (contract) before or alongside the implementation. Example, Order service: GET /orders/123 to fetch an order, POST /orders to create one. Other teams build against the contract without knowing the internals — less ambiguity, parallel work.

Serverless computing & Function-as-a-Service

The whole idea: you write a function; the cloud provider runs it, scales it, and bills you only when it runs. Servers still exist — you just don't manage them.

Analogy — taxi vs owning a car A VM is a car you own: you pay whether it moves or not, and you service it. A serverless function is a taxi: you pay per ride, someone else maintains the fleet.
  • FaaS examples: AWS Lambda, Azure Functions, Google Cloud Functions. Write code in Java/Python/etc., deploy it, and attach a trigger — an HTTP request, a file upload, or a message arriving in a queue.
  • Flow: trigger event → Lambda receives event → environment runs function → function processes input → returns result.
  • Functions are stateless by design: each invocation is independent. To remember anything (e.g. a stored order) use external storage — S3, RDS, DynamoDB.
Three core parts of a serverless web app
PartRoleAWS examples
ComputeRuns application logicLambda, Fargate
Data storeStores/retrieves dataDynamoDB, S3, Aurora Serverless
GatewayReceives requests, routes to functionAPI Gateway

Worked exampleFollow a request: "get my profile"

1. Client sends GET /profile/42 → API Gateway (routing).

2. Gateway invokes the Lambda function (business logic).

3. Lambda queries DynamoDB (storage) for user 42.

4. Lambda returns the profile; the gateway sends it back to the client.

Second flow from the lecture: user uploads a document → stored in S3 → upload event triggers Lambda → Lambda processes it → saves metadata in DynamoDB. No VM left running.

One-page summary

Memorise — Session 2 on one card Needs: zero downtime, short feedback cycles, multi-device, data-driven + 11 quality attributes. Shifts: monolith→microservices, on-prem→cloud, VM→container, one pipeline→pipeline per service. Models: enabled (legacy uses cloud bits) < based (lift-and-shift) < native (designed for cloud). Self-check

Q1. A bank keeps its core on a mainframe but sends notifications through a cloud service. Which cloud model?
Cloud-enabled — a legacy application that merely uses some cloud services; its main architecture and hosting are unchanged.
Q2. Why can a cloud-based app still scale badly even though it runs on auto-scaling infrastructure?
Because lift-and-shift keeps the internal architecture. If it is a monolith, the whole application has to be scaled together, so scalability depends on the application's design, not just the infrastructure.
Q3. List four limitations of a monolith.
Technology barrier (hard to mix stacks), poor scalability (scale everything), growing complexity, and difficult maintenance (changes to shared code affect unrelated features). Also: one failing test can block the single release pipeline.
Q4. During a sale, payment succeeded but the order service was down. Name two safeguards.
Idempotency keys (a retry doesn't charge twice), durable event queues (the order event isn't lost), and compensating transactions (refund/undo if the order can't complete).
Q5. Prime Video moved a workload from microservices to a single process and saved ~90%. Does that mean microservices are bad?
No. It shows architecture should follow requirements. Their components exchanged lots of data, so network calls, serialisation and extra infrastructure dominated cost. Keeping them in one process removed that overhead.
Q6. Why are Lambda functions stateless, and how do you keep state?
Each invocation runs independently and does not rely on data stored in a previous execution. Persist state in an external service such as S3, RDS or DynamoDB, which all invocations can share.
Q7. Scenario: 5 teams ship one app and releases are constantly blocked by a single failing test. Which architecture would you recommend and why?
Microservices with a pipeline per service: each team builds, tests and deploys independently, so one failing test only blocks its own service — provided the team can handle the added distributed-system complexity.
