What an API actually is

From the recording: an API is "a structured way for a software to communicate" — a set of rules and protocols describing exactly what a client can ask for and exactly what shape the response will take, without either side needing to know how the other is implemented internally.

Analogy — a restaurant menu, not the kitchen A menu is a contract: it tells you exactly what you can order (the available operations), what information you need to provide (a size, a spice level — the request parameters), and what you'll get back (the dish, described precisely enough that you know what's coming). You never need to know how the kitchen actually cooks it — gas stove or induction, which supplier the vegetables came from. An API is that same contract for software: it specifies the URL (which "dish" you're ordering), the authentication required (are you a member, do you have a reservation), the request parameters and data format (usually JSON), and the response shape — while the actual implementation behind the API is free to change completely without you ever noticing, as long as the contract holds.

HTTP verbs, with a dog-walking app

REST APIs are built around standard HTTP methods, each with a specific meaning by convention:

VerbMeaningDog-walking app example
GETRead, no side effectsGET /walks/42 — check the status of walk #42
POSTCreate something newPOST /walks — schedule a brand-new walk
PUTReplace/update an existing resourcePUT /walks/42 — change walk #42's time
DELETERemove a resourceDELETE /walks/42 — cancel walk #42

A good API design question the course keeps returning to: "what operations are available, what information must the client send, what response will the server return, and how are errors represented" — exactly the four questions the menu analogy above answers.

REST vs. GraphQL vs. gRPC

Analogy — ordering food, three ways REST is a fixed combo-meal menu: each endpoint returns a fixed shape of data, so you sometimes get more than you wanted (over-fetching — the combo comes with fries you didn't want) or have to place several separate orders to get everything you need (under-fetching — no combo has exactly your three items, so three separate orders). GraphQL is a buffet where you fill out one order form specifying precisely which items and how much of each — one request, exactly the data shape you asked for, nothing more. gRPC is the dedicated phone line between the kitchen and the delivery driver — not meant for the customer at all, but for fast, binary-encoded, service-to-service calls inside the restaurant's own backend, where speed matters more than human-readability.
RESTGraphQLgRPC
Data formatUsually JSONJSON, client-specified shapeProtocol Buffers (binary)
Best forPublic, simple, cacheable APIsComplex clients needing precise, varied data per screenFast internal service-to-service calls (microservices)
Typical weaknessOver-/under-fetchingHarder to cache; more server-side complexityNot human-browsable; needs generated client code

API contracts & semantic versioning

OpenAPI is the standard way to formally specify a REST API's contract — every endpoint, parameter, and response shape, machine-readable enough that tools can auto-generate client code, mock servers, and documentation directly from it (hence "OpenAPI Generators" in Session 1's sub-topics).

Analogy — sequel numbering for a movie franchise Semantic versioning (MAJOR.MINOR.PATCH, e.g. 2.1.3) works like how a film franchise signals how much continuity carries over. A MAJOR bump is a full reboot — the old contract no longer holds, callers must adapt (think a studio rebooting a franchise with a new timeline). A MINOR bump adds a new character or subplot without breaking what came before — existing callers keep working, new capability is simply available if you want it. A PATCH bump is fixing a continuity error or plot hole without changing the story at all — nothing for existing integrations to even notice.

Where this leads this semester

Session 1's API fundamentals are the foundation everything else in this course is built on top of — you'll be calling, not training, every AI capability you use: Module 5 wraps Hugging Face, computer vision, NLP, and speech recognition entirely as API calls, then goes deeper into Language Models specifically (LLM vs. SLM, LLMOps, LangChain, and a full RAG pipeline with its own evaluation metrics). None of that requires you to train a Transformer yourself, but it does require knowing what a token, an embedding, and an LLM actually are under the API you're calling.

Worth reading before Session 9 The Prerequisites Primer covers exactly that background — tokens, embeddings, and why today's LLMs are decoder-only — so the "Language Models" half of Module 5 isn't a black box.

Self-check

Q1. A mobile app screen needs exactly three specific fields from a user's profile, a dashboard screen needs twelve different fields, and a REST endpoint only returns the full 20-field profile object every time. What problem is this, and which alternative API style was designed to fix it?
This is over-fetching — the client receives more data than it needs in both cases (and if it needed data split across multiple REST endpoints, that would be under-fetching, requiring multiple round trips). GraphQL was designed specifically to fix this: the client specifies exactly which fields it wants in a single query, and the server returns exactly that shape — no more, no less.
Q2. Two microservices inside the same backend need to exchange data thousands of times per second with minimal latency. Would you reach for REST/JSON or gRPC, and why?
gRPC — it uses Protocol Buffers, a compact binary format, instead of human-readable JSON text, which serializes/deserializes faster and transmits less data over the wire. REST/JSON's readability is valuable for public, human-facing, or loosely-coupled APIs, but that same readability is overhead you don't need for tight internal service-to-service calls.
Q3. An API provider ships a change that adds a new optional field to a response but doesn't remove or rename anything existing. Under semantic versioning, is that a MAJOR, MINOR, or PATCH bump?
MINOR — new, backward-compatible functionality was added (existing callers are unaffected and can simply ignore the new field, or start using it if they choose), which is exactly the definition of a MINOR version bump under semantic versioning. A MAJOR bump is reserved for breaking changes; a PATCH is reserved for backward-compatible bug fixes with no new functionality.
