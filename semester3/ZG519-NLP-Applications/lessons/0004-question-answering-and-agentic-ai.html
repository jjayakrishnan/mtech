The QA task Book §11.5

The whole idea: the user asks a question (an information need written as a question) and the system returns an answer, ideally the exact answer span or a short generated sentence. Datasets of questions annotated with answers are used both to instruction-tune and to evaluate QA ability.

SettingWhat the system getsExample
Reading comprehension (older task)A question and a document; must extract the answer from itSQuAD-style
Open-book QAQuestion + one or more retrieved documents (e.g. via RAG, Session 3)A RAG chatbot over company manuals
Closed-book QAThe question only — the LLM answers from what it memorised during trainingAsking a bare LLM "Who wrote Frankenstein?"

The terms come from exams: students may or may not "open their books". A dataset can be used either way — Natural Questions is open-book if you use its attached passage, closed-book if not; MMLU is only closed-book.

Datasets and how they differ

Datasets vary along several dimensions: purpose (natural information-seeking vs probing/test questions), language, answer format (multiple-choice vs free text) and prompting (zero-shot vs few-shot).

DatasetKindDetails
Natural Questions (Kwiatkowski et al., 2019)NaturalAnonymised English Google queries; annotators answer from Wikipedia with a paragraph-length long answer and a short span answer. E.g. "When are hops added to the brewing process?" → short answer the boiling process
MS MARCONatural1 million real Bing questions + human-written answers + 9 million passages; tests both retrieval ranking and QA
DuReaderNatural, ChineseSearch-engine queries and community QA
TyDi QANatural, multilingual204K question–answer pairs in 11 typologically diverse languages (Arabic, Bengali, Kiswahili, Russian, Thai…). Task: pick the passage containing the answer (or NULL) and mark the minimal answer span
MMLUProbing15,908 knowledge/reasoning questions in 57 subjects (medicine, law, computer science…) from human exams; multiple-choice; zero- or few-shot; closed-book only

Why the distinction mattersNatural vs probing

MMLU questions test knowledge for academic or licensing purposes — they do not represent what people actually want to know. Natural Questions and MS MARCO come from real users, so they measure the real task a QA product faces. Keep both in mind when someone quotes a benchmark score.

Evaluating QA Book §11.6

Two metrics, chosen by answer type:

  • Exact match (EM) — for multiple choice or a single known answer: the percentage of predictions that match the gold answer exactly.
  • Token F1 — for free-text answers: treat the prediction and the gold answer as bags of tokens, compute F1 for each question, then average over all questions.
$$ P=\frac{|\text{pred}\cap\text{gold}|}{|\text{pred}|}\qquad R=\frac{|\text{pred}\cap\text{gold}|}{|\text{gold}|}\qquad F_1=\frac{2PR}{P+R} $$

Worked exampleBook's Natural Questions answer

Gold: the boiling process (3 tokens). Prediction: boiling process (2 tokens).

EM: not identical → 0.

Token F1: overlap = {boiling, process} = 2. \( P=2/2=1.0 \), \( R=2/3=0.667 \). \( F_1=2(1.0)(0.667)/(1.0+0.667)=\mathbf{0.80} \).

So F1 gives partial credit where EM gives none. (Many public QA evaluations also lowercase and strip articles and punctuation before comparing — which would make this prediction an exact match; state your normalisation when you compute.)

Worked exampleAveraging over a test set

Three questions: F1 = 1.0, 0.80, 0.0; exact match = 1, 0, 0.

Average F1 \( =(1.0+0.8+0.0)/3=\mathbf{0.60} \). EM \( =1/3=\mathbf{33.3\%} \). The model looks better on F1 because it gets partial credit for the near-miss.

Try it — exact match and token F1

For free-form generation (long answers, summaries, conversation) there is no single right string. The book's answer (§1.9.3) is people or LLMs as judges; add citation/faithfulness checks for RAG answers (Session 3). Also beware data contamination: public benchmarks leaking into training data inflate scores.

A short history of QA systems Book, Historical Notes last rows summarised

EraSystem / ideaHow it worked
1961BASEBALLAnswered questions about baseball games by parsing the question and matching it to a structured database (Place = ?, Team = Red Sox, Month = July, Day = 7)
1964ProtosynthexBuilt a query from the question's content words, retrieved sentences ranked by frequency-weighted overlap, and picked the one whose dependency structure best matched the question ("What do worms eat?" matches "worms eat grass", not "birds eat worms")
1970sLUNARNatural-language interface to a lunar-geology database; parsed questions into logical forms
1990sSemantic parsing, GeoQueryQA as machine learning: map the question to a formal query; later neural methods mapped text to SQL
1992–1999TREC QA trackAnnual evaluations of IR-based factoid and non-factoid QA; children's reading-comprehension tests used to evaluate machine comprehension (Hirschman et al., 1999)
2011IBM Watson DeepQALarge feature-based system built for Jeopardy!, just before neural systems took over
2015–2020Neural reading comprehension, then dense retrieval + span readerRetrieve passages with dense vectors, extract an answer span, often end to end
2019 →LLMs and RAGPretraining stores enough knowledge to answer questions closed-book; retrieval augmentation (first used to improve word prediction) was quickly applied to QA

The pattern: from hand-built knowledge bases and parsers → statistical IR + feature engineering → neural retrieval + reading → LLM generation with retrieval. The old ideas survive inside modern systems (databases and SQL are back as agent tools).

Introduction to agentic AI techniques

What an agent is Book §1.8

An agent is an LLM with the power to autonomously act in the world by calling other programs — a search engine for up-to-date information, a calendar to compute free slots, a calculator for maths, a database lookup, a supplier's API to order goods. It does so through a set of actions (like SEARCH(), CALENDAR(), CALCULATOR()) that it can generate in its output. The book stresses the intuition is the same as ordinary language models — token prediction; the actions are added to the set of tokens the model may generate. The shift from chat assistant to autonomous agent is large: great promise and many safety risks.

Analogy — a research assistant Ask a friend a hard question. A closed-book friend answers from memory. An agentic friend says "let me look that up", searches, reads, realises they need a second fact, searches again, then tells you the answer and where they found it.

ReAct: Reason → Act → Observe Book §1.8

In the ReAct framework (Yao et al., 2023) the model is prompted to produce actions interleaved with reasoning traces. It loops through three stages until the task is solved:

  1. Thought — reason about the goal and plan the next step.
  2. Action — call a tool.
  3. Observation — read what the tool returned. All history is added to the text context, then the loop repeats.

The book's sample ReAct prompt defines three simple actions: Search[entity] (look up the exact entity on Wikipedia; if absent, return similar entities), Lookup[keyword] (next sentence in the current passage containing the keyword), and Finish[answer] (return the answer and stop).

Worked exampleBook Fig. 1.16 — a multi-hop question answered by ReAct

Question: "Aside from the Apple Remote, what other device can control the program Apple Remote was originally designed to interact with?"

This cannot be answered in one search: first find which program, then find what else controls it. Step through below.

Step through the ReAct trace
  • Observation 2 shows error recovery: "Front Row" wasn't found, but the tool returned similar entities, so the agent reasons it should search "Front Row (software)".
  • Four loops (Thought → Act → Obs) were needed; a one-shot RAG that retrieves once might have missed the second hop. That is the multi-hop idea from Session 3, now driven by the model itself.

Worked exampleAn agentic text-to-SQL answer (designed)

Question: "How many orders above ₹500 were placed in October 2026?" Tool available: run_sql(query) over a table orders(id, amount, order_date).

Thought 1: I need a count with two filters on the orders table.

Action 1: run_sql("SELECT COUNT(*) FROM orders WHERE amount > 500 AND order_date BETWEEN '2026-10-01' AND '2026-10-31'")

Observation 1: [(1284,)]

Thought 2: The result is a count of 1,284. I can answer.

Action 2: Finish["1,284 orders"] — numbers like this are impossible to get from a closed-book model or from text retrieval, which is exactly why tools matter. (The count 1,284 is made up for illustration.)

Design checklist for a QA system

  1. Clean the input (spell check, normalisation — Session 2).
  2. Decide whether to retrieve and from where (agent-based RAG).
  3. Retrieve and rerank; keep citations (Session 3).
  4. Generate grounded in the passages; instruct "answer only from the provided sources".
  5. Verify (reflection / grader) and loop if the evidence is weak.
  6. Evaluate: EM / token F1 on a labelled set, retrieval P@k / AP, faithfulness; LLM-as-judge for free-form.
  7. Guard: limit tools, log actions, human approval for anything irreversible.

Practice questions

Q1. Gold answer "Mary Shelley"; prediction "Mary Wollstonecraft Shelley". Compute EM and token F1.
EM = 0 (strings differ). Tokens: gold {Mary, Shelley} (2), prediction {Mary, Wollstonecraft, Shelley} (3), overlap = 2. P = 2/3 = 0.667; R = 2/2 = 1.0; F1 = 2(0.667)(1.0)/(0.667+1.0) = 0.80.
Q2. A model answers 4 questions with token F1 = 1.0, 0.5, 0.5, 0.0 and exact match 1, 0, 0, 0. Report both metrics.
Average F1 = (1 + 0.5 + 0.5 + 0)/4 = 0.50; EM = 1/4 = 25%.
Q3. Gold "the Treaty of Versailles" (4 tokens), prediction "Treaty of Versailles signed 1919" (5 tokens). Token F1?
Overlap = {Treaty, of, Versailles} = 3 (case-insensitive; "the" is not in the prediction). P = 3/5 = 0.6, R = 3/4 = 0.75, F1 = 2(0.6)(0.75)/(1.35) = 0.9/1.35 = 0.667.
Q4. Is MMLU open-book or closed-book, and why does it not represent real users' needs?
Closed-book only (no passages attached). Its questions come from human exams to probe knowledge, not from people seeking information, so it tests knowledge/reasoning rather than the real information-seeking task.
Q5. Explain each stage of ReAct using the Apple Remote example.
Thought: decide to search Apple Remote to find its original program. Action: Search[Apple Remote]. Observation: the page says the Front Row media-centre program. Next Thought: now search Front Row; Action Search[Front Row] fails with similar entities; Thought: choose "Front Row (software)"; Observation: it is controlled by an Apple Remote or keyboard function keys; Action: Finish[keyboard function keys].
Q6. Why can a closed-book LLM not answer "How many orders above ₹500 did we get in October?" but an agent can?
The data lives in the company's database and changes daily; the model never saw it. An agent can generate a SQL query as an action, run it, and read the number from the observation.
Q7. Name two risks of agents compared with plain RAG.
Errors compound across loop steps, and the agent can take real-world actions (calling APIs, ordering, deleting) so a wrong action has consequences; also higher cost and latency from many LLM calls. Mitigate with guardrails, limited tool permissions, logging and human approval.
