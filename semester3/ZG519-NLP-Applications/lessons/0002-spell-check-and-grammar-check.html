Why spell/grammar check still matters (even for LLMs)

The whole idea: in an agentic system everything runs on text, so a typo in = distorted intent out. Models clean input and output as a built-in pre-processing and post-processing step.

WhereWhat goes wrong without it
Query normalisation"wether in Pune" must become "weather in Pune" before intent is understood
RAG retrievalA misspelled query gives the wrong embedding → irrelevant chunks retrieved
Agent actions / tool callsWrong tool name or arguments → error; malformed JSON output breaks the next step
Generated output (emails, reports)Must be polished and grammatical
Multi-step agent pipelinesAn error in one agent's output propagates to the next
HallucinationBad input or output text can lead to wrong answers
User trustTypos and ungrammatical replies make users distrust the system
API costGarbled prompts waste tokens, then need re-asking (extra calls) — important when optimising enterprise token spend

Where you use it daily: Word, e-mail, phone keyboards, WhatsApp (which learns your past mistakes), documentation.

Dictionary-based: edit distance

Analogy — how many pencil strokes to fix it? The edit distance between two words is the smallest number of single-character edits (pencil strokes) needed to turn one into the other. Small distance = probably a typo of that word.

Damerau–Levenshtein allows four operations (each cost 1):

OperationMeaningExample (typed → correct)
Deletion errorA letter is missing in what you typedacress → actress (missing t)
Insertion errorAn extra letter was typedacress → acres (extra s) / cress
SubstitutionOne letter replaced by anotheracress → access (r→c) / across (e→o)
TranspositionTwo adjacent letters swappedacress → caress (ac→ca)

Most mistakes are within 1–2 characters (distance 1 covers ~80% of typos), so systems only search that small neighbourhood to save time and latency. The limit is tunable by language, domain and application. Dictionary look-up uses Levenshtein (dynamic programming) or a trie / BK-tree; tries/prefix trees also power auto-complete. A top-K list of closest words is shown to the user.

Side notePhonetic matching: Soundex

For speech-to-text style errors ("phone" vs "fone", Smith vs Smyth) Soundex assigns each word a short code (first letter + digits for consonants, vowels dropped) and matches similar codes — same idea as edit distance but on sound. Not examined in depth; the focus is text.

Worked exampleEdit distance of "weather" vs "wether" and "cat" vs "cta"

weather → wether: delete one "a" → distance 1 (a deletion error).

their → thier: swap "ei" ↔ "ie" → with transposition allowed, distance 1 (plain Levenshtein would need 2 substitutions).

cat → cta: swap "at" ↔ "ta" → distance 1.

Dynamic programming idea: \( D(i,j) = \min\big(D(i-1,j)+1,\ D(i,j-1)+1,\ D(i-1,j-1)+[a_i\ne b_j]\big) \), and for transposition also \( D(i-2,j-2)+1 \) when \( a_i=b_{j-1} \) and \( a_{i-1}=b_j \).

Statistical: the noisy-channel model

Analogy — a bad phone line You meant to say word w, but it travelled down a noisy channel (your clumsy fingers) and arrived as x. We try to work out which original word w most likely produced what we received — like guessing what someone said on a crackly line.

For an observed misspelling \( x \), choose the vocabulary word \( w \) with the highest posterior (Bayes' rule). The denominator \( P(x) \) is the same for every candidate, so it is dropped:

$$ \hat{w} = \arg\max_{w\in V} P(w\mid x) = \arg\max_{w\in V} \underbrace{P(x\mid w)}_{\text{likelihood (channel model)}}\ \underbrace{P(w)}_{\text{prior (language model)}} $$
TermNameHow to get it
\( P(w) \)Prior (language model)Easy: count how often \( w \) occurs in a big correct corpus ÷ total words. (Real values are tiny, e.g. \( 10^{-20} \); take logs.) No labels needed
\( P(x\mid w) \)Likelihood (channel model)Count how often people typed x when they meant w, from an error corpus of (wrong, right) pairs — e.g. Peter Norvig's spelling error data — using the four edit operations

Zero counts are fixed with add-one (Laplace) smoothing, just as in Naive Bayes: add 1 to the numerator and the vocabulary/character count to the denominator. Training data matters: everything boils down to counts, even in transformers. Candidates come from edit distance 1 (or 2) in the dictionary.

Worked exampleCorrecting "acress" — unigram only

Candidates within edit distance 1 (illustrative textbook-style values, ×10⁻⁹ shown for readability):

CandidateEdit\( P(w) \)\( P(x\mid w) \)\( P(x\mid w)P(w)\times10^{9} \)
actressdelete t0.00002310.0001172.7
acrosssubstitute e→o0.0002990.00000932.8
acresinsert s0.00003180.00003211.0

Step 1 — multiply prior × likelihood for each candidate (e.g. actress: \( 0.0000231 \times 0.000117 = 2.7\times10^{-9} \)).

Step 2 — compare. The top two are almost tied: across 2.8 vs actress 2.7. The small ones (access, caress, cress) can be ignored. Unigram alone picks across — but the professor asked the class: "is this sufficient?" Answer: no — we need context.

Worked exampleAdding context with bigrams: "…a stellar and versatile acress whose combination of sass and glamour…"

Multiply the channel probability by the bigram probabilities of the word with its neighbours (previous word versatile, next word whose) — order matters:

\( P(\text{actress}\mid\text{versatile}) = 0.000021 \), \( P(\text{whose}\mid\text{actress}) = 0.0010 \)

\( P(\text{across}\mid\text{versatile}) = 0.000021 \), \( P(\text{whose}\mid\text{across}) = 0.000006 \)

actress: \( 0.000117 \times 0.000021 \times 0.0010 = 2.5\times10^{-12} \)

across: \( 0.0000093 \times 0.000021 \times 0.000006 = 1.2\times10^{-15} \)

Actress now wins by ≈ 2,000×. Take-away: unigram + bigram (trigram optional, with weights) is usually enough; "whose" after "across" almost never happens. This is why SymSpell and similar tools also use context. Compute is tiny — a CPU is enough, no API fee.

Real-word errors

Why different? A non-word is flagged by the dictionary. A real word is valid, so any word in the sentence might be wrong, and each word must itself be a candidate (the word could be right). Choosing the best candidate needs the probability of the whole sequence, via the chain rule.

Worked examplePhrase "two of few" (candidate sets)

Edit-distance-1 candidate sets including the word itself: word 1 → 4 options, word 2 → 3 options, word 3 → 4 options (as in the lecture slide).

Brute force: every combination → \( 4\times 3\times 4 = 48 \) sequences — grows exponentially with sentence length.

Simplifying assumption (one error per phrase): fix two words as correct and vary only the third:

\( (4-1) + (3-1) + (4-1) = 3 + 2 + 3 = 8 \) alternatives (plus the original sentence).

Procedure: (1) compute \( P \) of the sequence for each alternative; (2) the highest tells you which word is most likely wrong; (3) then proceed exactly as for a non-word: edit-distance candidates → noisy channel → bigram/trigram context → arg max. Same idea as Viterbi: take the max at each step.

Student question: "What if the sentence is long?" Break it into sub-phrases (noun phrase / verb phrase) or use a context window of ±2 words — like limiting attention to nearby tokens. Very long dependencies are where attention models help.

ML and transformer approaches

  • Framing: a multi-class classification problem — classes are the possible corrections (e.g. the edit-distance-1 candidates). Needs labelled (incorrect → correct) data; features (hand-built for classic ML such as SVM): context words, POS tags, whether the word is in the dictionary, edit distance. Deep models (RNN/LSTM) learn features automatically. Whether 20 parameters in an SVM or billions in an LLM, you are learning weights.
  • Spell check → encoder-only (BERT-style) is enough: you emit one word at a time.
  • Grammar check → encoder–decoder (T5-style): it is sequence-to-sequence — feed in the whole incorrect sentence, generate the corrected sentence.
  • GECToR (grammar error correction) is a transformer tagger: for each word it predicts an edit tag — keep, replace, delete…
  • LLMs can be fine-tuned with PEFT (LoRA / QLoRA) or small language models (e.g. Qwen) used, possibly with RAG for a domain. QLoRA / quantization: store weights in fewer bits (32-bit floats → 4-bit / NF4) to save memory and compute at some accuracy cost.
  • Research is active in 2026, especially multilingual (covered later with machine translation).

Student questionLanguages change — how do models cope?

Vocabulary changes (Gen-Z vs Shakespeare) but grammar rules are largely stable. What the model knows is decided by its training corpus. Word meanings also drift (broadcast: scattering seeds → media), and contextual embeddings plus attention capture meaning from context.

Grammar check pipeline

  1. Spell check first (assume spellings are right before checking grammar).
  2. Tokenize and tag. Rule-based: POS tagging, tokenization, parsing by rules. Statistical: HMM + Viterbi for POS tagging. Neural: encoder–decoder.
  3. Parse. Dependency parsing shows relations between words; statistical constituency parsing; neural parsers.
  4. Check subject–verb–object agreement, tense, articles, punctuation.
  5. Suggest — either auto-correct, or show options and let a human choose (human in the loop).

Simple SVO checks are fine with rules; context-heavy cases need neural models.

Evaluation — precision, recall, F-score

Always needs a ground truth — the correct text to compare against. In practice, count at the level of edits (corrections the system proposes).

Analogy — the proof-reader Imagine a proof-reader going through your essay. Precision: of everything she circled, how much was a real mistake? Recall: of all the real mistakes in the essay, how many did she circle?

Settling the in-class debateWhat is "positive" here?

Several students argued about false positive vs false negative. The cleanest way to settle it: define the positive event as "an error is flagged / an edit is made."

  • True positive (TP): there is an error and the system flags/corrects it correctly.
  • False positive (FP): there is no error (or the edit is wrong), but the system flags it anyway — an unnecessary or wrong correction. (A sentence like "they play" that is already right but gets changed.)
  • False negative (FN): there is an error but the system misses it and leaves it as is. (Spelling "definately" left untouched; "He are happy" not corrected.)
  • True negative (TN): no error, system correctly leaves it alone.

The student's confusion came from reading "negative" as "the system says it's incorrect". In this setting, flagging an error is the positive prediction, so flagging a correct sentence = FP. The professor planned a simpler example next class.

$$ \text{Precision}=\frac{TP}{TP+FP}\qquad \text{Recall}=\frac{TP}{TP+FN}\qquad F_\beta=\frac{(1+\beta^2)\,P\,R}{\beta^2 P + R},\quad F_{0.5}=\frac{1.25\,P\,R}{0.25\,P+R} $$
  • Why F0.5? It weights precision more than recall. In spell/grammar checking we hate unnecessary corrections (LLMs tend to over-correct), so a wrong flag hurts more than a missed one. F1 balances them equally.
  • Precision = 1 means every suggestion the system made was correct. Low recall means it found few of the real mistakes.

Worked example10 flags, 8 right

System flags 10 words as errors; 8 are real errors (TP = 8), 2 are not (FP = 2). Precision = \( 8/10 = 0.8 \).

Worked exampleRecall — 5 real errors, 2 found

A paragraph has 5 real spelling mistakes; the system finds only 2 (TP = 2, FN = 3). Recall = \( 2/5 = 0.4 \) — low recall.

Worked exampleFull calculation with F0.5

Test text has 10 real errors. The system proposes 8 edits: 6 correct (TP = 6), 2 wrong or unnecessary (FP = 2). It missed 4 errors (FN = 4).

Precision = \( 6/(6+2) = 0.75 \). Recall = \( 6/(6+4) = 0.60 \).

F₁ = \( 2\cdot0.75\cdot0.60/(0.75+0.60) = 0.90/1.35 = 0.667 \).

F0.5 = \( 1.25\cdot0.75\cdot0.60/(0.25\cdot0.75+0.60) = 0.5625/0.7875 = 0.714 \).

F0.5 > F1 because precision (0.75) is higher than recall (0.60) and F0.5 rewards precision.

Self-check

Q1. Why does an LLM-based agent still need spell check?
Typos distort intent, damage retrieval quality in RAG, break tool names/arguments and JSON, cause hallucinations, hurt user trust and waste API tokens. Models therefore normalise input and polish output as pre/post-processing.
Q2. Non-word vs real-word error — why different techniques?
A non-word is detected by dictionary lookup and corrected from nearby dictionary words. A real word is valid in the dictionary, so every word is suspect and must be judged in context; you need sequence probabilities (chain rule/n-grams) to detect which word is wrong.
Q3. For "acress", why is unigram probability not enough?
"across" (2.8) narrowly beats "actress" (2.7) on prior × channel alone. In "a versatile ___ whose…", the bigrams P(actress|versatile) and P(whose|actress) are far higher than for "across", so context reverses the ranking.
Q4. A phrase has candidate-set sizes 5, 4, 3 (including the original words). Combinations under brute force vs one-error-at-a-time?
Brute force: \( 5\times4\times3 = 60 \). One-error-at-a-time: \( (5-1)+(4-1)+(3-1) = 4+3+2 = 9 \) alternatives.
Q5. TP = 9, FP = 1, FN = 6. Compute precision, recall and F0.5.
P = 9/10 = 0.9; R = 9/15 = 0.6; F0.5 = 1.25·0.9·0.6 / (0.25·0.9 + 0.6) = 0.675 / 0.825 ≈ 0.818.
Q6. Why is F0.5 preferred over F1 for grammar correction?
Because unnecessary or wrong corrections annoy users more than missed ones, so precision should count more than recall. F0.5 weights precision more heavily.
Q7. Which transformer architecture for spell check and which for grammar check?
Spell check: encoder-only (BERT-style) is sufficient. Grammar check: encoder–decoder (T5-style) because it maps a whole sentence to a corrected sentence.
