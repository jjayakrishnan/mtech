1 · The Power and Limits of LLMs

Analogy

An LLM is like a brilliant scholar who memorized a vast library at a point in time — but is now locked in a room with no new books. They're great at reasoning but can't know what happened after the door closed, and they might confidently misremember details they only partially learned.

What LLMs Are Great At

  • Generating fluent, human-like text
  • Summarization, translation, and content creation
  • Answering questions based on vast training data
  • Reasoning, code generation, few-shot learning

Inherent Limitations

LimitationDescriptionExample
Knowledge CutoffKnowledge frozen at training timeCan't answer about events after training
HallucinationsGenerates plausible but false information"The CEO of X is Y" (wrong name)
Lack of SpecificityNo access to private/proprietary knowledgeCan't answer about your company's internal policy
No live dataCan't look things up in real-timeCurrent stock prices, today's news

2 · The RAG Solution

Definition

Retrieval-Augmented Generation (RAG) combines an information retrieval system with a language model. Instead of retraining the LLM with new data (expensive), RAG gives the LLM access to a live, external knowledge base at query time — grounding its responses in retrieved facts.

Core Components

  • Retriever: Finds relevant document chunks from the knowledge base given the user query
  • Generator: Takes the query + retrieved chunks as context, generates a grounded answer
  • Knowledge Base: Company docs, PDFs, databases, SharePoint, Confluence, product manuals…
Why RAG over Fine-Tuning?
  • Cost: Fine-tuning requires GPU compute + curated data; RAG needs only a vector store.
  • Freshness: RAG knowledge base can be updated without retraining.
  • Transparency: RAG can cite its sources; fine-tuned models cannot.
  • Domain: RAG works for proprietary data; fine-tuning risks leaking private data.

3 · Semantic Search (The Retrieval Engine)

Keyword vs Semantic Search

Query: "cost of laptop repair"
Keyword: Only matches documents containing "cost", "laptop", "repair" literally. Misses: "pricing for computer hardware fixes".
Semantic: Converts query and documents to dense embedding vectors; finds closest by cosine similarity — catches "pricing" ≈ "cost", "computer hardware" ≈ "laptop".

Embedding-Based Retrieval

  1. Split the knowledge base into chunks (e.g., 512-token paragraphs)
  2. Encode each chunk as a dense vector using an embedding model (e.g., sentence-BERT, DPR)
  3. Store vectors in a vector database (FAISS, Pinecone, Weaviate)
  4. At query time: encode the query, compute cosine similarity with all stored vectors
  5. Retrieve top-k chunks and pass to the LLM
$$\text{sim}(q, d) = \cos(\mathbf{e}_q, \mathbf{e}_d) = \frac{\mathbf{e}_q \cdot \mathbf{e}_d}{\|\mathbf{e}_q\| \cdot \|\mathbf{e}_d\|}$$

Thresholding vs Ranking

Two Selection Strategies
  • Ranking (top-k): Select the k highest-scoring chunks regardless of absolute score. Always returns k results.
  • Thresholding: Select all chunks with similarity ≥ threshold. May return fewer or more depending on query.

Example: Scores = [0.94, 0.88, 0.81, 0.74, 0.69], threshold = 0.80 → pass 3 chunks {0.94, 0.88, 0.81} to LLM. Chunks below 0.80 are discarded to reduce noise.

4 · The RAG Pipeline

End-to-End RAG Flow
  1. User Query: "What is our policy on international travel?"
  2. Embed Query: Convert query to dense vector using embedding model
  3. Semantic Search: Find top-k relevant chunks from HR policy docs vector store
  4. Context Retrieval: Retrieve: "Overseas Business Trips and Expense Approval" section
  5. Prompt Enhancement: Construct prompt: "Using the following context: [retrieved text], answer: What is our policy on international travel?"
  6. LLM Generation: Generate grounded, accurate answer — preventing hallucination

Indexing Phase (Offline)

-- Build knowledge base index (run once) documents = load_knowledge_base() chunks = split_into_chunks(documents, size=512) embeddings = embedding_model.encode(chunks) vector_store.add(embeddings, chunks)

Retrieval Phase (Online)

-- At query time (run for every user question) query_embedding = embedding_model.encode(query) top_k_chunks = vector_store.search(query_embedding, k=5) prompt = f"Context: {top_k_chunks}\nQuestion: {query}\nAnswer:" response = llm.generate(prompt)

5 · Token Budgeting

Context Window Constraint

Every LLM has a fixed maximum context window. This window must hold: system instructions + user query + retrieved chunks. If total tokens exceed the window, earlier content is truncated. Retrieval must be carefully budgeted.

$$\text{Available tokens} = \text{Max context} - (\text{System prompt} + \text{User query})$$
Worked Example: Token Budget Calculation
  • Maximum context length: 8,192 tokens
  • System prompt: 300 tokens
  • User query: 220 tokens
  • Available for retrieved chunks: \(8192 - (300 + 220) = 7672\) tokens
  • Each chunk size: 512 tokens
  • Maximum chunks: \(\lfloor 7672 / 512 \rfloor = 14\) chunks

Why floor? Exceeding the context limit causes truncation — partial chunks are useless or harmful.

Exam Trap

Always use \(\lfloor \cdot \rfloor\) (floor), never ceiling or rounding. Exceeding the window is not permitted. If a question gives you available tokens and chunk size, the answer is always floor division.

6 · Knowledge Graph–Enhanced RAG

Standard RAG retrieves chunks of raw text. KG-enhanced RAG also queries a Knowledge Graph (KG) for structured facts, enabling more precise, structured retrieval.

ApproachRetrievalStrengthWeakness
Standard RAGDense vector chunksHandles natural language wellMay retrieve noisy, loosely related text
KG-RAGSPARQL + vectorPrecise structured facts; no hallucination on known entitiesRequires KG to be built and maintained
Agentic RAGMulti-step retrievalCan chain queries, verify factsMore complex; higher latency

In Agentic RAG, the LLM acts as an agent: it decides what to retrieve, when to retrieve, and can iteratively refine its queries based on intermediate results. This is the "RAG 2.0" direction.

7 · BM25 vs Dense Retrieval

AspectBM25 (Sparse)Dense (bi-encoder)Hybrid
RepresentationSparse TF-IDF vectorsDense embedding vectorsBoth combined
SimilarityKeyword overlap + saturationCosine of embeddingsWeighted sum
Semantic understandingNone — exact match onlyStrong — synonym/paraphraseBest of both
SpeedVery fast (inverted index)Slower (ANN search)Moderate
Training neededNoYes (contrastive training)Yes (both)
BM25 score: $$\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1 + 1)}{f(t,d) + k_1 \cdot (1 - b + b \cdot \frac{|d|}{\text{avgdl}})}$$

where \(f(t,d)\) = term frequency, \(|d|\) = document length, \(k_1 \approx 1.5\), \(b = 0.75\).

9 · Practice Questions

Q1 · Why does RAG use semantic search rather than keyword search?

Keyword search matches only exact words — "cost of laptop repair" would miss "pricing for computer hardware fixes" even though the meaning is the same. Semantic search embeds both query and documents into a dense vector space where semantically similar sentences are geometrically close. Cosine similarity retrieves relevant documents regardless of exact wording. This is critical for natural language queries where users rarely use the same vocabulary as the documents.

Q2 · Calculate max chunks given: context=16384, system=500, query=300, chunk=1024.

Available = 16384 − (500 + 300) = 15584 tokens. Max chunks = ⌊15584 / 1024⌋ = 15 chunks. (15584 / 1024 = 15.21… → floor = 15).

Q3 · What is the difference between top-k ranking and threshold-based retrieval?

Top-k ranking: Always returns exactly k chunks — the k with highest similarity scores, regardless of absolute value. Risk: may include irrelevant chunks if all scores are low.
Thresholding: Returns all chunks with similarity ≥ threshold. May return 0 chunks (nothing relevant) or many. Risk: hard to choose threshold; query-specific behavior.
In practice, top-k is more predictable for token budgeting; thresholding is better for precision.

Q4 (6-mark) · Explain the full RAG pipeline and why it outperforms a plain LLM for enterprise Q&A.

Offline (indexing): Documents are chunked into 512-token segments → embedded with a sentence encoder (e.g., sentence-BERT) → stored in a vector database.
Online (retrieval): User query is embedded → cosine similarity search finds top-k relevant chunks → chunks injected into prompt as context → LLM generates a grounded answer.
Why it beats plain LLM:
1. Freshness: Knowledge base updated without retraining.
2. Specificity: Company-internal documents never seen in public training data.
3. Anti-hallucination: LLM instructed to answer only from provided context.
4. Traceability: Retrieved chunks can be shown as citations.
5. Cost: Much cheaper than full fine-tuning and retraining. RAG is the standard architecture for enterprise LLM deployments.
