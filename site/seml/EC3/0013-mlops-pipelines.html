What is MLOps?

Definition

MLOps (Machine Learning Operations) is the practice of applying DevOps principles to ML systems. It covers the entire lifecycle from data collection to model retirement, with emphasis on automation, reproducibility, monitoring, and collaboration between data scientists and operations teams.

Analogy — Manufacturing quality control

A car manufacturer doesn't just design a car once and ship it. Every car on the assembly line is tested at each stage; defects are caught before shipping; processes are continuously improved. MLOps is the assembly-line thinking applied to ML: automated testing at every stage, continuous delivery of improved models, and monitoring every model in production.

MLOps Maturity Levels

LevelCharacteristicsTrigger for retraining
0 — ManualScripts, notebooks, manual handoff to opsAd-hoc, when someone notices degradation
1 — Automated pipelineML pipeline automated; model deployed automatically on triggerScheduled (weekly) or on data change
2 — Full CI/CDPipeline code is versioned; testing automated; multiple environments (dev/staging/prod)On code change OR data drift OR performance drop

The instructor noted: "MLOps is about predictive AI — the classic ML models. LLMOps adds language model specifics (prompt versioning, token cost monitoring). AgentOps adds agent-specific concerns on top."

ML Pipeline Stages

A production ML pipeline has these stages, each automated and tested:

StageWhat happensKey artefacts
1. Data ingestionPull data from sources (DB, S3, API); validate schemaRaw dataset, ingestion log
2. Data validationCheck schema, distributions, duplicates, nullsValidation report, data profile
3. PreprocessingClean, transform, feature engineering, splitFeature dataset, preprocessing code version
4. TrainingTrain model on train set; log hyperparams, metricsModel weights, training run ID
5. EvaluationScore on test set; compare to baseline; fairness checksEvaluation report, model card
6. RegistryPush to model registry if evaluation passes thresholdRegistered model version (Staging)
7. DeploymentBlue/green or canary deployment to serving infraServing endpoint, deployment manifest
8. MonitoringTrack drift, performance, system healthDashboards, alerts, retraining triggers
What triggers retraining?

Three triggers for automated retraining: (1) schedule — retrain weekly regardless, (2) data trigger — new data volume exceeds threshold or drift detected, (3) performance trigger — model accuracy drops below threshold. Exam question: "What are the three triggers for automated retraining in a mature MLOps pipeline?"

MLFlow

MLFlow's four components
  • Tracking — log experiments: hyperparameters, metrics, artefacts, and source code version
  • Projects — package ML code for reproducibility (MLproject file with conda/pip env)
  • Models — standard model format with flavours (sklearn, pytorch, tensorflow, pyfunc)
  • Registry — centralised model store with versioning and lifecycle stages

Tracking API

import mlflow import mlflow.sklearn

mlflow.set_experiment("churn-prediction")

with mlflow.start_run() as run:
  # Log hyperparameters
  mlflow.log_param("n_estimators", 100)
  mlflow.log_param("max_depth", 5)
  mlflow.log_param("learning_rate", 0.01)

  model = GradientBoostingClassifier(n_estimators=100, max_depth=5)
  model.fit(X_train, y_train)

  # Log metrics
  mlflow.log_metric("train_auc", roc_auc_score(y_train, model.predict_proba(X_train)[:,1]))
  mlflow.log_metric("test_auc", roc_auc_score(y_test, model.predict_proba(X_test)[:,1]))

  # Log the model artefact
  mlflow.sklearn.log_model(model, "model", registered_model_name="churn-classifier")

  # Log any file as artefact
  mlflow.log_artifact("feature_importance.png")
run_id is the key to reproducibility

Every MLflow run gets a unique run_id. Given a run_id, you can: re-load the exact model (mlflow.sklearn.load_model(f"runs:/{run_id}/model")), view every hyperparameter and metric, and check the git commit that produced it. This is reproducibility by design.

Model Registry

The model registry is a central catalogue of all model versions with their lifecycle stage:

StageMeaningWho promotes?
NoneNewly registered; not reviewedCI pipeline (auto)
StagingPassed evaluation; ready for integration testingCI pipeline (auto, if metrics pass)
ProductionApproved; actively serving requestsHuman approval gate (or automated if trusted)
ArchivedSuperseded or deprecated; kept for auditAutomated on new Production promotion
# Promote a model version to Production via API
from mlflow.tracking import MlflowClient

client = MlflowClient()
client.transition_model_version_stage(
  name="churn-classifier",
  version=7,
  stage="Production"
)

# Load the current Production model
model = mlflow.pyfunc.load_model("models:/churn-classifier/Production")
Registry vs artefact store

The artefact store (S3, Azure Blob, GCS) holds the raw model files. The registry holds metadata about those files: which version is Production, who approved it, what run_id produced it. The registry references artefacts by URI — it does not duplicate them. Examiners sometimes ask: "What does the model registry store?" Answer: metadata + lifecycle stage, not the model weights themselves.

CI/CD for ML

CI/CD for ML has two trigger types (unlike software CI/CD which only triggers on code change):

ML CI/CD triggers
  • Code change trigger — developer pushes to main → pipeline runs tests, retrains, evaluates, deploys
  • Data change trigger — new data arrives (daily batch, stream threshold) → pipeline reruns from preprocessing stage

GitHub Actions pipeline for ML

name: ML Pipeline
on:
  push: {branches: [main]}
  schedule: [{cron: "0 2 * * 1"}] # Every Monday 02:00 UTC

jobs:
  train-and-deploy:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - name: Validate data
      run: python scripts/validate_data.py
    - name: Train model
      run: python scripts/train.py
    - name: Evaluate & gate
      run: python scripts/evaluate.py --min-auc 0.82
    - name: Register to MLflow
      run: python scripts/register_model.py
    - name: Deploy to Kubernetes
      run: kubectl apply -f k8s/model-deployment.yaml

Versioning Everything

The instructor emphasised: "In a mature MLOps pipeline, we version three things — code, data, and pipeline. Not just code."

ArtefactToolWhat to version
CodeGitTraining scripts, preprocessing code, evaluation code
DataDVC, Delta Lake, LakeFSDataset snapshots — every training run links to exact data version
PipelineMLflow Projects, KubeflowThe pipeline DAG definition — not just the model
ModelMLflow RegistryModel weights + metadata (params, metrics, run_id, data version)
EnvironmentDockerContainer image digest (not just tag — tags are mutable)
Why version the pipeline?

The pipeline is not just the model — it's the preprocessing steps, feature engineering, and evaluation logic. If the pipeline changes, the model comparison is invalid (you're not comparing apples to apples). Versioning the pipeline means you can replay any historical training run exactly.

Exam Prep

High-probability exam questions
  • What are the stages of an ML pipeline? Name 6 stages in order.
  • Explain MLFlow tracking. What does mlflow.log_param vs mlflow.log_metric do?
  • What are the four lifecycle stages in the MLFlow Model Registry?
  • What triggers retraining in a mature MLOps pipeline? Name three triggers.
  • Why must we version data, not just code? What tool enables data versioning?
QuestionOne-line answer
MLFlow log_param vs log_metric?log_param: discrete config (n_estimators). log_metric: continuous measure (test_auc). Metrics can track over steps.
Registry stages?None → Staging → Production → Archived.
Data versioning tool?DVC (Data Version Control) — git-style versioning for large data files.
3 retraining triggers?Schedule, data change/drift, performance degradation.
Difference: MLOps vs LLMOps?MLOps = predictive models (tabular, CV). LLMOps adds prompt versioning, token cost, hallucination monitoring.
