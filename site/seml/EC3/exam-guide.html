Session 9 · Agentic AI Frameworks 10 marks

Likely Question

Explain the ReAct (Reason + Act) loop used by autonomous LLM agents, naming its three core steps and how the loop terminates. Then compare LangChain, CrewAI, and AutoGen as agentic frameworks in tabular form, and state which one you would pick for a given multi-agent scenario.

a. Explain the ReAct loop with a diagram and a worked trace. 4 marks

b. Compare LangChain vs CrewAI vs AutoGen in a table and justify a framework choice for a scenario. 6 marks

How to structure the answer

Don't just draw the loop — name the three steps in order, show one full worked cycle, and say explicitly how the agent knows to stop. For the table, examiners reward a differentiator per row over vague adjectives: instead of "CrewAI is simpler," say why (fixed role/task abstraction vs. a general-purpose graph you must design yourself).

9a · The ReAct Loop: Thought → Action → Observation

Think of a detective solving a case with no fixed script. She doesn't silently think through the whole case and announce a verdict (that's plain chain-of-thought reasoning — all in her head, ungrounded). Instead she works in short bursts: form a hypothesis about what to check next (Thought), go check it — interview a witness, examine a record (Action), read what came back (Observation), and only then form her next hypothesis. She repeats this cycle, each round grounded in real evidence, until she has enough to close the case. That loop — reason, act on the world, observe the result, reason again — is exactly the ReAct pattern (Yao et al., 2022) that autonomous LLM agents use.

The three steps, precisely
  • Thought — the model's internal reasoning, in natural language: what do I know so far, what's missing, what should I do next? It is never executed — it only decides the next Action.
  • Action — a structured call to an external tool chosen by the Thought, e.g. Search[query], Calculator[expr], an API call, or a code-execution call.
  • Observation — the real result returned by that tool, appended to the model's context. It is not generated by the model — it comes from the outside world, which is what grounds the next Thought in fact rather than hallucination.

The loop repeats — Thought2 is conditioned on Observation1, and so on — until a Thought concludes "I have enough evidence," at which point the agent emits a terminal Finish[answer] instead of another tool call.

Worked trace — a classic multi-hop ReAct example (in the style of Yao et al.'s HotpotQA demonstrations):

Q: What is the elevation of the tallest mountain in the country that hosted the 2016 Summer Olympics? Thought 1: I need to find which country hosted the 2016 Olympics. Action 1: Search[2016 Summer Olympics host country] Observation 1: Brazil. Thought 2: Now I need the tallest mountain in Brazil. Action 2: Search[tallest mountain in Brazil] Observation 2: Pico da Neblina. Thought 3: Now I need the elevation of Pico da Neblina. Action 3: Search[Pico da Neblina elevation] Observation 3: 2,995 metres. Thought 4: I have host country, mountain, and elevation — no further search is needed. Action 4: Finish[2,995 metres]
Common mistake

Writing the cycle out of order (e.g. "Action, then Thought, then Observation") or describing ReAct as "just chain-of-thought prompting." Plain chain-of-thought never touches the real world — it reasons in one unbroken block and can hallucinate a fact halfway through with nothing to correct it. ReAct's Observation is a genuine, external, unpredictable result; that grounding is the entire point and is worth stating explicitly for marks.

Memorise

Thought → Action → Observation, repeat, then Finish[answer]. Thought never touches the world; Action does; Observation is what the world sends back.

9b · LangChain vs CrewAI vs AutoGen

All three let an LLM call tools and (with extra setup) coordinate several agents, but they start from different mental models: LangChain gives you a general toolbox and, via LangGraph, an explicit state graph you wire up yourself; CrewAI gives you a fixed "team" abstraction (roles, goals, tasks) with almost no wiring; AutoGen treats multi-agent systems as a conversation between agents, with a first-class ability to write and execute code.

Core mental modelChains/tools; LangGraph adds an explicit node-and-edge state graphA crew of role-based agents (role, goal, backstory) working through tasksAgents as conversational participants exchanging messages
Multi-agent orchestrationVia LangGraph: you define nodes (agents/functions) and edges (control flow) explicitlySequential or hierarchical task hand-off; a manager agent can delegateGroup chat with a manager selecting the next speaker, or nested chats

Human-in-the-loopLangGraph interrupt breakpoints pause the graph for approvalA per-task "human input" flag pauses for user inputUserProxyAgent makes HITL a first-class, built-in agent type

Worked example — applying the table to a scenario

Scenario: "Build a 3-agent pipeline — a Researcher gathers information, a Writer drafts a report, an Editor reviews it — with minimal setup time."

Pick CrewAI. The scenario is exactly CrewAI's native abstraction: three named roles with clear goals, handed off sequentially. LangGraph could do it too, but you'd hand-wire the graph nodes and edges yourself for no extra benefit here; AutoGen's conversational/code-execution strengths aren't needed since no agent is executing or debugging code. Stating why the other two are a worse fit, not just naming the right one, is what earns full marks on a justify-your-choice question.

Common mistake

Claiming "LangChain doesn't support multi-agent orchestration." It does — via LangGraph — it's just not a bundled, opinionated abstraction the way CrewAI's Crew or AutoGen's GroupChat are. Say "more effort to wire up," not "can't do it."

Try it yourself

Name one advantage AutoGen has over CrewAI when an agent needs to write and debug Python code, and explain why.

AutoGen has a native, sandboxed code-execution agent: generated code is actually run, and its stdout/stderr is fed back automatically as the next Observation, so the agent can see its own error and retry — a built-in ReAct-style debug loop. CrewAI has no equivalent first-class capability; you would have to hand-write a custom Tool that wraps a code interpreter and manually pipes the output back into the task context.

Session 11 · Data & Concept Drift 10 marks

Likely Question

Distinguish data drift from concept drift with an example of each. Explain the Population Stability Index (PSI), compute it for a given distribution, and state the action triggered at each threshold band.

a. Distinguish data drift from concept drift, with examples and a diagram. 4 marks

b. Explain PSI, work a numeric example, and give the 0.1 / 0.2 threshold actions. 6 marks

How to structure the answer

The examiner is testing whether you know retraining is not automatic just because "something changed." Say explicitly which kind of change forces a retrain and which doesn't. For the PSI part, show the formula, plug in real numbers, and land on a verdict against the threshold table — a bare formula with no worked numbers loses marks.

11a · Data Drift vs Concept Drift

A model is a frozen snapshot of a relationship it learned between inputs and outputs. Two different things can go stale after deployment: the inputs you're feeding it can start looking different from training, or the real-world relationship between inputs and outputs can itself change underneath the model. These are data drift and concept drift — and only one of them always demands a retrain.

Analogy — a tailor's measurements

A tailor who fitted you five years ago made a rule: "waist size → shirt size." Data drift is your body shape changing — the tailor is now measuring different waist sizes than before, but the rule "this waist → this shirt" is still valid. Concept drift is the shirt-sizing standard itself changing — the same waist measurement now maps to a different shirt size, so the tailor's old rule gives the wrong answer even for a customer whose waist never changed.

Precise definitions
  • Data drift (covariate shift) — \( P(X) \) changes: the distribution of inputs shifts, but \( P(Y|X) \) (the true relationship) still holds. Example: a model trained on customers aged 25–45 now serves customers aged 60+ — the inputs are out of distribution, but "this profile → this outcome" may still be correct.
  • Concept drift — \( P(Y|X) \) changes: the relationship between inputs and outputs itself shifts. Example: a fraud model trained pre-COVID flags remote-work expense claims and online-shopping surges as fraud — the world changed what "normal" spending looks like, so the model's concept of fraud is stale.
Exam trap

Data drift: inputs change → the model may still be correct if the decision boundary still holds. Concept drift: the correct decision itself changes → retraining is always required. You can have data drift without concept drift and vice versa — always name which one you're diagnosing before recommending an action.

Memorise

Data drift = inputs move, rule may still work. Concept drift = the rule itself breaks. \( P(X) \) vs \( P(Y|X) \) — that's the whole distinction.

11b · Population Stability Index (PSI)

PSI is a single number that compares a reference distribution (training data) against a current one (production data), bucketed into bins:

$$ PSI = \sum_{i=1}^{k} \left( P_{prod,i} - P_{ref,i} \right) \cdot \ln\!\left(\frac{P_{prod,i}}{P_{ref,i}}\right) $$

Worked example — feature: customer income bracket, 4 bins:

BinReference %Production %(Prod−Ref)·ln(Prod/Ref)
< ₹30k0.200.15(−0.05)·ln(0.75) = 0.0144
₹30k–60k0.400.35(−0.05)·ln(0.875) = 0.0067
₹60k–100k0.300.300.00·ln(1) = 0.0000
> ₹100k0.100.20(0.10)·ln(2.0) = 0.0693
PSI = sum of last column0.0904
Reading the verdict

0.0904 is just under 0.1 — despite the top income bin doubling in share, the other three bins barely moved, so the combined shift is still classified negligible. This is exactly why you compute PSI rather than eyeballing one bin: one large-looking change can still net out to "no action" once weighed against the rest of the distribution.

PSI valueInterpretationAction
< 0.1Negligible changeNo action
0.1 – 0.2Moderate shiftInvestigate
> 0.2Significant driftRetrain model
Common mistake

Treating PSI > 0.2 on any single feature as automatic proof of concept drift. PSI only tells you \(P(X)\) has moved (data drift). Whether the model's accuracy has actually degraded (concept drift) needs a separate check against ground-truth labels once they arrive — PSI is an early-warning signal, not a verdict on model correctness.

Try it yourself

A feature's PSI comes back as 0.15. According to the threshold table, what should you do — and why is this different from what you'd do at PSI = 0.25?

PSI = 0.15 falls in the 0.1–0.2 band — investigate, not retrain: check which bins moved, whether it correlates with a known event (new marketing campaign, seasonal effect), and watch the trend over the next few monitoring windows. At PSI = 0.25 (> 0.2), the action escalates to retrain the model immediately rather than just watching — the shift is large enough that waiting risks serving predictions on data the model was never trained to handle.

Session 12 · Docker 10 marks

Likely Question

Precisely distinguish a Docker image from a container. Explain why Dockerfile instruction order affects build caching, with a worked before/after example.

a. Image vs container — precise distinction. 4 marks

b. Explain caching and instruction order with a worked example and diagram. 6 marks

How to structure the answer

Students lose marks by using "image" and "container" interchangeably in the same sentence. Pin the distinction to one clean line each, then a consequence. For 12b, don't just say "put COPY requirements.txt first" — explain why a cache miss at one layer invalidates every layer after it, using the exact Dockerfile lines.

12a · Image vs Container

Analogy — a cake recipe vs a baked cake

An image is the recipe card plus a photo of every intermediate step — a fixed, read-only description of how to build something. A container is an actual cake baked from that recipe, sitting on your counter, that you can now cut into, add icing to, or eat — changes to it don't rewrite the recipe card. Bake ten cakes from the same recipe card and you have ten independent containers from one image.

DimensionImageContainer
What it isA read-only template built from a Dockerfile's layersA running (or stopped) instance of an image
MutabilityImmutable — never changes after buildHas its own writable top layer for runtime changes
MultiplicityOne image can produce many containersEach container is an independent instance
Lifecycle verbdocker builddocker run (creates), docker stop (halts)
PersistenceStored in a registry (Docker Hub, ECR, GCR)Writable layer is lost on removal unless committed or a volume is used
Common mistake

Saying docker run "creates an image." It does not — it creates a container from an existing image. The image itself is only produced by docker build. Getting this verb pairing right (build→image, run→container) is often exactly what the mark scheme checks.

12b · Instruction Order and Layer Caching

Every Dockerfile instruction (FROM, COPY, RUN, ...) produces one immutable layer, cached by a hash of that instruction plus its inputs. On a rebuild, Docker walks the instructions top to bottom and reuses a cached layer only until the first one whose hash changed — every layer after that point is rebuilt from scratch, even if their own inputs didn't change, because each layer's cache key also depends on the layer before it.

Worked example — the fix in code

Bad (invalidates pip install on every commit):

FROM python:3.11-slim WORKDIR /app COPY . . ⇐ copies source too — changes every commit RUN pip install -r requirements.txt ⇐ cache key now depends on the line above CMD ["uvicorn", "main:app"]

Good (pip install cached until dependencies actually change):

FROM python:3.11-slim WORKDIR /app COPY requirements.txt . ⇐ only this small file first RUN pip install -r requirements.txt ⇐ cached — reused every build COPY src/ . ⇐ source changes land here, last CMD ["uvicorn", "main:app"]
Common mistake

Stopping at "copy requirements.txt before source code" and forgetting OS-level dependencies. The full rule is: order every instruction from least-frequently-changing to most-frequently-changing — base image → system/apt packages → language dependencies (requirements.txt / package.json) → application source → runtime config. Missing the system-package step is a common partial-credit loss.

Memorise

A cache miss at one layer invalidates every layer after it. Order Dockerfile instructions least-changing → most-changing: base image, system deps, language deps, then source code last.

Try it yourself

You add one new line, RUN apt-get install -y libpq-dev, directly above COPY src/ . in the "good" Dockerfile above. Is this the best position for it? Why or why not?

No — it should move up, right after FROM and before COPY requirements.txt .. System packages like libpq-dev change even less often than Python dependencies, so placing it late means every source-code edit forces Docker to reinstall an OS package that never changed. The correct order is: base image → system packages → language dependencies → source code.

Session 13 · MLflow 10 marks

Likely Question

Name and briefly describe MLflow's four components. Describe the model registry's four lifecycle stages with a diagram. State three triggers that cause a production model to be retrained.

a. MLflow's four components. 3 marks

b. Registry stages with a diagram, including who promotes each transition. 4 marks

c. Three retraining triggers, one line each. 3 marks

How to structure the answer

Four components means four named things, each with a one-line job — a paragraph blurring them together loses marks. For the registry, draw the stage flow left-to-right and label who moves a model between stages; the classic trap is claiming the registry stores model weights (it doesn't — it stores metadata pointing at them).

13a · MLflow's Four Components

Analogy — a research lab

Tracking is the lab notebook (every experiment's settings and results, dated and signed). Projects is the standard equipment-setup checklist so any lab can reproduce your experiment exactly. Models is a universal adapter plug so the finished result works regardless of which "socket" (framework) it came from. Registry is the promotion ladder — HR's official record of which experiment is now "on the job" in production.

ComponentJob
TrackingLogs experiments — hyperparameters, metrics, artefacts, and the source-code version for every run
ProjectsPackages ML code for reproducibility (an MLproject file plus a conda/pip environment)
ModelsA standard model format with "flavours" (sklearn, pytorch, tensorflow, pyfunc) so any tool can load it the same way
RegistryCentralised, versioned model store with lifecycle stages and promotion history

Worked example — Tracking API for one training run:

with mlflow.start_run(): mlflow.log_param("n_estimators", 100) mlflow.log_metric("test_auc", 0.87) mlflow.sklearn.log_model(model, "model", registered_model_name="churn-classifier")
Common mistake

Naming only "Tracking" and "Registry" and forgetting Projects and Models exist as separate components — a "name the four components" question checks for exactly four distinct names, not two described twice.

13b · Model Registry Lifecycle Stages

StageMeaningWho promotes?
NoneNewly registered, not yet reviewedCI pipeline (auto)
StagingPassed evaluation, ready for integration testingCI pipeline (auto, if metrics pass)
ProductionApproved, actively serving requestsHuman approval gate
ArchivedSuperseded or deprecated, kept for auditAutomated on the next Production promotion
Common mistake

Claiming the registry stores the model weights themselves. It stores metadata — which version is Production, who approved it, which run_id produced it — and references the actual weight files sitting in a separate artefact store (S3, GCS, Azure Blob) by URI. It does not duplicate them.

13c · Three Retraining Triggers

TriggerWhat fires itExample
ScheduleA fixed time interval, regardless of anything elseCron job retrains every Monday 02:00 UTC
Data triggerNew data volume crosses a threshold, or drift (PSI/KS) is detected10,000 new labelled rows have arrived since last training
Performance triggerA live metric drops below an acceptable floorProduction AUC falls from 0.87 to 0.79

Memorise

MLflow = Track, Package, Standardise, Register. Stages: None → Staging → Production → Archived. Retrain on: Schedule, Data, Performance.

Try it yourself

A model's production AUC has been stable, but the data team says 50,000 new labelled transactions arrived overnight. Which retraining trigger applies, and would you also check anything from Session 11 before deciding?

This is a data trigger (new data volume crossed a threshold) — not a performance trigger, since AUC hasn't dropped. Before deciding, it's worth checking PSI on key features first: if the new data's distribution closely matches the reference (low PSI), retraining may just reinforce the existing model; if PSI is elevated, the new data likely reflects a real shift worth incorporating.

Session 14 · AgentOps 10 marks

Likely Question

Distinguish MLOps, LLMOps, and AgentOps. List RAGAS's four evaluation metrics. State the criterion for requiring a human-in-the-loop (HITL) checkpoint, with two examples.

a. The three ops levels, with a diagram. 3 marks

b. RAGAS's four metrics, one line each. 4 marks

c. The HITL criterion, with two contrasting examples. 3 marks

How to structure the answer

The three ops levels are additive, not a replacement sequence — say so explicitly, it's a common examiner check. For HITL, state the actual decision rule ("blast radius") before giving examples; two examples with no stated rule only earns partial credit.

14a · MLOps → LLMOps → AgentOps

ConcernMLOpsLLMOpsAgentOps
ArtefactSklearn/PyTorch weightsLLM + system promptAgent config + tools + LLM
EvaluationAccuracy, F1, AUCRAGAS, G-Eval, human ratingsTask completion, tool accuracy
Retraining triggerDrift / performance dropPrompt update / fine-tuneAgent goal drift / new tool
Common mistake

Describing AgentOps as replacing MLOps. It doesn't — an agent still has an underlying LLM whose cost/latency needs LLMOps, and if any component is a classic ML model (e.g. a ranking model used as a tool), it still needs MLOps drift monitoring. Each layer adds concerns on top of the one below; none of them are optional once you're at the next layer.

14b · RAGAS's Four Metrics

RAGAS scores a RAG pipeline's answer against the question and the retrieved context on four axes:

MetricWhat it checks
FaithfulnessAre the claims in the answer actually supported by the retrieved context (no hallucinated facts)?
Answer RelevancyDoes the answer actually address the question asked?
Context RecallHow much of the ground-truth answer is covered by what was retrieved?
Context PrecisionWhat fraction of the retrieved chunks were actually relevant (not noise)?
Worked example

Question: "What year was BITS Pilani founded?" — Retrieved context: one chunk about BITS Pilani's founding in 1964, one unrelated chunk about its Dubai campus. Answer given: "BITS Pilani was founded in 1964 and has a campus in Goa."

  • Faithfulness — high: "1964" is supported by the retrieved chunk; but "Goa" is not in the context at all — that claim is unsupported, so faithfulness is dinged for the hallucinated detail.
  • Answer Relevancy — high: the core answer (1964) directly addresses the question.
  • Context Recall — high: the founding-year fact needed for the ground truth was retrieved.
  • Context Precision — low: half the retrieved chunks (the Dubai-campus one) were irrelevant noise.
Common mistake

Confusing Context Recall with Context Precision. Recall asks "did we retrieve everything we needed?" (missing chunks hurt recall). Precision asks "was everything we retrieved actually useful?" (irrelevant chunks hurt precision). A retriever can score high on one and low on the other.

14c · Human-in-the-Loop (HITL)

The decision rule

Not every agent action needs a human gate. The test is: "what is the blast radius if this step is wrong?" Low or no blast radius (read-only, easily reversible) → let the agent act autonomously. High or irreversible blast radius → require human approval before the action executes.

Agent actionBlast radiusHITL?
Search the web / summarise a documentNone — read-onlyNo
Send an email to 10,000 customersHigh — reputational riskYes — require approval
Delete a database tableCritical — irreversibleYes — explicit confirmation
Implementation patterns
  • Interrupt + resume — agent pauses at the checkpoint, notifies a human, waits, then continues (LangGraph interrupt nodes)
  • Shadow mode first — agent proposes the action but doesn't execute until approved (good for bulk actions)
  • Confidence thresholding — auto-execute above a confidence threshold, escalate below it

Memorise

MLOps → LLMOps → AgentOps is additive, not a replacement. RAGAS: Faithfulness, Answer Relevancy, Context Recall, Context Precision. HITL rule: high or irreversible blast radius → require a human gate.

Try it yourself

An agent drafts a refund of ₹200 to one customer (auto-approved under a ₹500 threshold) vs a bulk refund of ₹50,000 across 300 customers. Apply the HITL rule to each.

The ₹200 single refund has a low, contained blast radius (one customer, below the confidence/amount threshold) — the agent can auto-execute it. The ₹50,000 bulk refund across 300 customers has a high blast radius (large financial impact, hard to reverse cleanly at scale) — it should be routed through a human approval gate before executing, even though each individual refund might look small.
