Why Do We Need Design Patterns for Agents?

A single ML model is easy to deploy — one container, one endpoint. But modern AI systems compose many agents: a data-fetching agent, a reasoning agent, a validation agent, a storage agent. When these agents collaborate on a long-running task, three hard problems emerge:

  • Partial failure — what if the 4th agent in a chain crashes after the first three have committed changes?
  • Coordination — how do agents share knowledge without tight coupling?
  • Rollback — distributed systems cannot use a single database transaction across microservices.
Analogy — Airport check-in

Flying involves a chain: check-in → security → boarding. If boarding is cancelled, the airline must compensate — refund baggage fees, cancel the security slot, free the seat. That compensation chain is exactly the Saga pattern applied to air travel. Each step has a corresponding undo action.

The SEML course covers three patterns that solve these problems for agent-based systems:

  • Saga — long-running distributed transactions with compensating rollback
  • Blackboard — shared knowledge store read/written by multiple specialist agents
  • Orchestration — central coordinator directing all agents (as distinct from choreography)

Saga Pattern

Definition

A Saga is a sequence of local transactions where each transaction publishes an event or sends a message to trigger the next. If any step fails, a series of compensating transactions are run to undo the work done by preceding transactions.

The Core Problem: No Global Transactions

In a microservices architecture — or an agent architecture — each agent has its own database. You cannot wrap all agent actions in a single ACID transaction (no distributed two-phase commit). The Saga pattern solves this by breaking the operation into local transactions with explicit compensation.

Worked Example: ML Training Pipeline

Suppose you have a 5-step ML pipeline run by separate agents:

StepAgent ActionCompensating Transaction
1. Data ingestionLock dataset, increment usage countUnlock dataset, decrement count
2. Feature storeWrite features to store, charge quotaDelete features, refund quota
3. GPU allocationReserve 4 × A100 GPUs for 2 hoursRelease GPU reservation
4. Training jobStart training, commit checkpointDelete checkpoint, stop job
5. Model registryRegister model version, publish eventDeregister version, retract event

If Step 4 fails (GPU OOM), the saga runs compensations for Steps 1–3 in reverse order: release GPUs → delete features → unlock dataset. The system reaches a consistent state without any global lock.

Exam trap

Compensating transactions are not rollbacks in the database sense. They are new forward-running transactions that undo the effect of a previous action. The previous transaction is still in the log — it completed successfully. The compensation adds new records to undo the effect.

Key Properties of Saga

  • Atomicity — the saga as a whole either completes all steps or compensates all completed steps
  • No locks held between steps — each local transaction commits immediately
  • Eventual consistency — the system converges to a consistent state, but not instantaneously
  • Idempotency required — each step and compensation must be safe to run more than once (network retries)

Orchestration vs Choreography

There are two ways to coordinate a Saga. The choice determines who knows about the overall sequence.

Orchestration-based Saga

A central Saga Orchestrator (a dedicated agent or microservice) tells each participant what to do and handles responses. Participants don't know about each other.

# Orchestrator pseudo-code
result1 = await data_agent.ingest(dataset_id)
if result1.ok:
  result2 = await feature_agent.compute(result1.data)
  if result2.ok:
    result3 = await gpu_agent.reserve(4)
    if not result3.ok:
      await feature_agent.compensate(result2.id) # undo step 2
      await data_agent.compensate(result1.id) # undo step 1
      raise SagaFailure("GPU unavailable")
Orchestration advantages
  • Saga logic is centralised — easy to understand and test
  • Orchestrator can be versioned and deployed independently
  • Works naturally with LangGraph, AWS Step Functions, Temporal
  • Participants are simple — they just respond to commands

Choreography-based Saga

There is no central coordinator. Each participant listens for events and publishes its own events. Other participants react to those events.

# Each service reacts to events on a message bus
DataAgent: on(SagaStarted) → ingest() → emit(DataIngested | DataFailed)
FeatureAgent: on(DataIngested) → compute() → emit(FeaturesReady | FeatureFailed)
GPUAgent: on(FeaturesReady) → reserve() → emit(GPUReserved | GPUFailed)
FeatureAgent: on(GPUFailed) → emit(FeaturesCompensated) # undo
DataAgent: on(FeaturesCompensated) → emit(DataCompensated) # undo
Choreography pitfall

Choreography is harder to debug. Because there is no central view of the flow, you need distributed tracing (e.g. OpenTelemetry) to reconstruct what happened. For exam answers: say "choreography scales better but is harder to observe; orchestration is easier to reason about but adds a coordination bottleneck."

Who controls flow?Central orchestratorEach participant reacts to events
CouplingParticipants coupled to orchestratorParticipants coupled to event schema
ObservabilityEasy — orchestrator logs all stepsHard — need distributed tracing

Blackboard Pattern

Definition

The Blackboard pattern uses a shared data store (the "blackboard") where multiple specialist agents — called knowledge sources — read the current state and write partial solutions. A controller decides which knowledge source acts next.

Analogy — Academic seminar

Imagine a whiteboard at the front of a conference room. A speech recognition expert writes a phoneme lattice. A grammar expert reads the lattice and writes candidate sentences. A semantics expert reads the sentences and writes the most likely interpretation. Each expert (knowledge source) reads from and writes to the shared whiteboard. Nobody talks directly to each other — they all talk through the board. That's the blackboard pattern.

Three Components

  • Blackboard — the shared data structure. Contains the current partial solution. All knowledge sources read/write here.
  • Knowledge Sources (KS) — specialist agents, each with a narrow capability (e.g. OCR agent, NER agent, sentiment agent). Each KS monitors the blackboard for data it can act on.
  • Controller — decides which KS fires next. Can use a rule-based scheduler, priority queue, or ML model to select the most promising KS.

Blackboard in Agent AI

In multi-agent LLM systems, the blackboard is often a vector store or a shared context dictionary. Example:

blackboard = {
  "raw_query": "What are Q3 revenue drivers?",
  "retrieved_docs": [...], # written by retriever agent
  "entities": ["Q3", "revenue"], # written by NER agent
  "summary": "...", # written by summariser agent
  "draft_answer": "...", # written by writer agent
  "final_answer": None # written by critic agent last }
When Blackboard wins
  • When the problem requires incremental refinement (speech recognition, complex NLP pipelines)
  • When knowledge sources have heterogeneous capabilities and no fixed order
  • When partial solutions from one domain help unlock progress in another (e.g. OCR output guides layout analysis)
Exam tip

The controller in the blackboard pattern is not an orchestrator. The orchestrator tells agents what to do (imperative). The controller in blackboard just selects which knowledge source is most suitable to act next — it does not tell it how to do it. Knowledge sources are self-triggered by blackboard state.

Pattern Comparison and Selection Guide

PatternControlData flowBest when…Avoid when…
Saga (Orchestration) Centralised orchestrator Command-response Complex multi-step transactions with many compensations needed Very high throughput (bottleneck risk)
Saga (Choreography) Decentralised (event bus) Events Simple chains, high volume, teams own separate services Complex compensations or when observability is critical
Blackboard Controller picks KS Shared store (read/write) Incremental refinement, heterogeneous KSes, partial solutions needed Simple linear pipelines (overkill)

AWS and Industry Adoption

AWS explicitly recommends the Saga pattern for microservice-based ML pipelines. AWS Step Functions implements the orchestration-based Saga natively — each state machine state maps to one local transaction, and the error handlers define compensating steps. The instructor noted: "AWS recognized that the Saga pattern, implemented through Step Functions, is the gold standard for distributed ML workflows."

LangGraph as orchestrator

LangGraph is a graph-based framework where nodes are agents and edges are transitions. When you define a LangGraph with error edges pointing to compensation nodes, you get an orchestration-based Saga implemented in Python. The supervisor node in LangGraph is the orchestrator; worker nodes are participants.

Exam Prep

High-probability exam questions
  • Explain the Saga pattern and why it is needed in microservices. Contrast with a 2PC transaction.
  • Compare orchestration-based Saga vs choreography-based Saga. Give one advantage of each.
  • Describe the three components of the Blackboard pattern and the role of each.
  • When would you choose Blackboard over Saga? Give a concrete ML example.
  • What is a compensating transaction? How does it differ from a database rollback?

Quick-answer cheatsheet

QuestionOne-line answer
What is a Saga?Sequence of local transactions + compensating transactions for distributed rollback.
Orchestration vs Choreography?Orchestration = central coordinator; Choreography = event-driven, no coordinator.
Blackboard controller role?Selects which knowledge source acts next — does NOT tell it how.
Compensating transaction vs rollback?Compensation is a new forward transaction that undoes effects; rollback reverts uncommitted changes.
