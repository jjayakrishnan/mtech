The Ops Stack: MLOps → LLMOps → AgentOps

The evolution

The instructor's framing: "MLOps is for predictive AI. LLMOps adds what's new for language models. AgentOps adds what's new for autonomous agents." Each layer adds new concerns on top of the previous one, not replacing it.

ConcernMLOpsLLMOpsAgentOps
Model artefactSklearn/PyTorch weightsLLM + system promptAgent config + tools + LLM
VersioningModel registry (MLFlow)Prompt versions + model versionsAgent config version + tool versions
EvaluationAccuracy, F1, AUC on test setRAGAS, G-Eval, human ratingsTask completion rate, tool accuracy, multi-turn coherence
MonitoringDrift, latency, throughputToken cost, latency, hallucination rateTrace length, tool call success, loop detection, goal completion
Retraining triggerDrift / performance dropPrompt update / fine-tuneAgent goal drift / new tool capability
Analogy — Adding floors to a building

MLOps is the foundation. LLMOps is the second floor — built on the foundation, adds new rooms (prompt management, token billing). AgentOps is the third floor — built on both, adds rooms for multi-agent coordination, tool monitoring, and human escalation. You can't build floor 3 without floors 1 and 2.

Observability for Agent Systems

Traditional observability uses logs, metrics, and traces. For agents, the same three pillars apply but with agent-specific semantics:

SignalTraditional meaningAgent-specific meaning
TracesRequest → response path through microservicesComplete agent session: user input → plan → tool calls → final answer
SpansOne microservice's contribution to a traceOne step in the agent loop: one LLM call, one tool execution, one memory retrieval
MetricsLatency, throughput, error rateTokens per request, tool call count, loop count, task completion rate
LogsStructured event recordsEvery LLM input/output, every tool call + result

Key AgentOps Metrics

  • Task completion rate — % of tasks where the agent reached a valid final answer
  • Tool call accuracy — % of tool calls that returned useful (non-error) results
  • Hallucination rate — % of agent outputs that contain factually incorrect claims (requires reference or LLM judge)
  • Loop detection — % of sessions where the agent looped (same Thought/Action more than 2 times)
  • Token efficiency — task completion tokens / total tokens spent
  • Latency p95 — 95th percentile end-to-end latency per user request
  • Human escalation rate — % of sessions that required human intervention
Exam trap — what's unique about agent monitoring

A standard model has one input → one output. An agent has a multi-step session with tool calls. You must monitor the session, not just individual LLM calls. Key differences: (1) agents can loop — need loop detection; (2) agents call tools — need tool success rate; (3) agents accumulate cost over many LLM calls — need per-session token budgets.

AgentOps SDK

AgentOps (agentops.ai) is an observability SDK for LLM agents. It auto-instruments LangChain, CrewAI, AutoGen and others.

import agentops from langchain_openai import ChatOpenAI

# Initialize — sends events to AgentOps dashboard
agentops.init(api_key="your-key", default_tags=["seml-demo", "production"])

# Your agent code runs normally — AgentOps intercepts LLM calls
llm = ChatOpenAI(model="gpt-4o")
result = agent.run("Summarise Q3 results") # auto-traced

# End session and get summary
agentops.end_session("Success", end_state_reason="Task completed")

# AgentOps captures:
# - Every LLM call: prompt, response, tokens, cost, latency
# - Every tool call: name, args, result, error (if any)
# - Session-level: total tokens, total cost, duration, outcome
What AgentOps logs per session
  • Session ID, start/end time, outcome (Success/Failure/Indeterminate)
  • Per LLM call: model, prompt tokens, completion tokens, cost, latency
  • Per tool call: tool name, arguments, return value, success/error
  • Per agent action: action type (Thought/Action/Observation), content

Agent Evaluation

Evaluating agents is harder than evaluating classifiers. There is no single number. Evaluation happens at three levels:

Level 1: Component Evaluation

  • Retriever quality (if RAG): precision@k, recall@k, MRR
  • LLM call quality: output relevance, factuality, format compliance
  • Tool precision: does the agent call the right tool with the right arguments?

Level 2: Task Evaluation

  • Task completion rate: did the agent achieve the stated goal?
  • Answer quality: rated by human or LLM judge (RAGAS, G-Eval)
  • Efficiency: steps taken, tokens used vs minimum possible

Level 3: Business Evaluation

  • User satisfaction: thumbs up/down, CSAT scores
  • Business KPIs: did the agent's outputs lead to conversions, cost savings, etc.?
  • Safety: % of responses that were harmful or policy-violating
Exam tip — three levels of evaluation

Exam questions often ask "how do you evaluate an agent system?" The key is to mention all three levels: component (retriever, tools), task (completion rate, answer quality), and business (KPIs, user satisfaction). A common mistake: only mentioning accuracy or F1 — those are for classifiers, not agents.

LLM Evaluation Frameworks

RAGAS (RAG Assessment)

RAGAS evaluates RAG pipelines on four metrics:

  • Faithfulness — are the claims in the answer supported by the retrieved context?
  • Answer Relevancy — how well does the answer address the question?
  • Context Recall — how much of the ground truth is covered by the retrieved context?
  • Context Precision — what fraction of retrieved chunks are actually relevant?

G-Eval (GPT-Eval)

G-Eval uses a strong LLM as a judge to score responses on custom criteria (coherence, fluency, relevance, factuality). The LLM is given a rubric and chain-of-thought steps, then asked to score 1–5.

# G-Eval: use GPT-4o as judge
prompt = """ You are evaluating a customer support agent response. Rate the response on FACTUALITY (1-5): 5 = All facts correct and verifiable 1 = Major factual errors Response: {response} Context: {context} Step by step: ... Final score (1-5):"""

TruLens

TruLens instruments LLM apps and evaluates them using "feedback functions" — any function that scores an input/output pair. Can use OpenAI, Cohere, or local models as judges. Integrates natively with LangChain and LlamaIndex.

FrameworkBest forKey metric
RAGASRAG pipeline evaluationFaithfulness, Context Recall
G-EvalCustom rubric evaluation via LLM judgeAny user-defined criteria (1–5 scale)
TruLensLangChain/LlamaIndex app monitoringFeedback functions (pluggable)

Human-in-the-Loop (HITL) Checkpoints

When to add HITL

Not every agent decision should be autonomous. HITL checkpoints add a human approval gate at high-risk steps. The key question: "What is the blast radius if this step is wrong?" High blast radius → HITL.

Agent actionBlast radiusHITL?
Search the webNone — read-onlyNo
Summarise a documentNone — read-onlyNo
Send an email to 1 personLowOptional
Send email to 10,000 customersHigh — reputational riskYes — require approval
Delete a database tableCritical — irreversibleYes — require explicit confirmation
Deploy to productionHigh — service impactYes — staged rollout + human gate
HITL implementation patterns
  • Interrupt + resume — agent pauses at a checkpoint, sends a notification, waits for human response, then continues (LangGraph interrupt nodes)
  • Shadow mode first — agent proposes action but doesn't execute until human approves (good for bulk actions)
  • Confidence thresholding — agent auto-executes when confidence > threshold; escalates when below (reduces human load)
Exam tip — HITL is not a bug, it's a feature

Examiners often frame questions as "when is full autonomy appropriate?" The answer: never for high-blast-radius actions with irreversible consequences. HITL is a design choice, not a fallback. A mature agent system has explicit HITL policies documented and tested.
