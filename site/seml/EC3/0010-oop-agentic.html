Why OOP Matters for Agentic AI

Agentic AI systems are software systems. The same principles that make large codebases maintainable — encapsulation, inheritance, composition — apply directly to agent design. But agents have unique requirements that make OOP especially valuable:

  • State encapsulation — an agent's memory, goals, and context must be isolated; global state causes race conditions in multi-agent systems
  • Polymorphism — a planner agent and a tool-use agent share an interface but behave differently; you can swap implementations without changing callers
  • Composability — complex agents are composed of simpler agents via inheritance or delegation
  • Testability — encapsulated agents can be unit-tested in isolation (mock the LLM, test the logic)
Analogy — Employee contract

Think of each agent as an employee with a job description. OOP is the HR contract: it defines what the employee knows (state / attributes), what they can do (methods), and what interface they expose to the rest of the organisation. Without it, you have chaos — everyone calling everyone else's private data directly.

Agent as a Class

The canonical OOP design for an LLM agent defines five core methods:

class BaseAgent:
  def __init__(self, name, llm, tools, memory_store):
    self.name = name
    self.llm = llm # LLM backend
    self.tools = {t.name: t for t in tools}
    self.memory = memory_store # encapsulated state
    self.goal = None

  def observe(self, input_data):
    """Update memory with new observations from env."""
    self.memory.add(input_data)

  def plan(self):
    """Use LLM to generate a plan given current memory."""
    return self.llm.invoke(self.memory.as_prompt())

  def act(self, plan):
    """Execute a plan step — call a tool or produce output."""
    tool = self.tools.get(plan.tool_name)
    return tool.run(plan.args) if tool else plan.output

  def remember(self, observation):
    """Persist an observation to long-term memory."""
    self.memory.store_long_term(observation)

  def run(self, task):
    """Main loop: observe → plan → act → remember."""
    self.observe(task)
    for _ in range(self.max_steps):
      plan = self.plan()
      if plan.is_final: return plan.output
      obs = self.act(plan)
      self.remember(obs)

Specialised Agents via Inheritance

class ResearchAgent(BaseAgent):
  """Adds web search capability and citation tracking."""
  def __init__(self, *args, **kwargs):
    super().__init__(*args, **kwargs)
    self.citations = []

  def act(self, plan):
    result = super().act(plan)
    self.citations.append(result.source) # extra behaviour
    return result
Exam tip — encapsulation

Encapsulation means agent memory is private. Never let one agent directly read or write another's self.memory. Inter-agent communication must go through a defined interface: message passing, a shared blackboard, or a coordinator. Violation = tight coupling = tests break when internals change.

Memory Implementation Patterns

  • ConversationBufferMemory — full message history in RAM. Simple but grows without bound.
  • ConversationSummaryMemory — LLM summarises old messages to keep context window small.
  • VectorStoreMemory — embeddings stored in a vector DB (Pinecone, Chroma). Retrieves relevant past context by semantic search.
  • Entity Memory — extracts named entities and stores structured facts about them.
Design rule: separate short-term from long-term memory

Short-term memory (the context window) is fast but expensive and bounded. Long-term memory (vector store or SQL) is slower but unlimited. A well-designed agent loads only relevant long-term memories into short-term memory for each task — like a professional consulting their notes before a meeting.

Data Structures for Agent Systems

Agents are not just LLM wrappers — they coordinate work using classic data structures:

Task Queue (FIFO or Priority)

When multiple tasks arrive, they go into a queue. A scheduler agent dequeues the next task based on priority.

import heapq
task_queue = []
heapq.heappush(task_queue, (1, "Summarise quarterly report")) # priority 1
heapq.heappush(task_queue, (3, "Draft email to team")) # priority 3
priority, task = heapq.heappop(task_queue) # returns priority 1 first

Dependency Graph (DAG)

When tasks depend on each other, model them as a Directed Acyclic Graph. The scheduler runs tasks in topological order.

# Task A → Task B → Task D
# → Task C → Task D
deps = {"B": ["A"], "C": ["A"], "D": ["B", "C"]}
# D cannot start until both B and C complete

Decision Tree for Routing

An orchestrator agent may use a decision tree to route tasks to the right specialist agent based on input classification.

When to use each
  • Queue — when tasks are independent and need throughput management
  • DAG — when tasks have dependencies (e.g. data ingestion before training)
  • Tree — when routing logic is hierarchical and deterministic
  • Graph (cyclic) — when agents can revisit previous states (LangGraph's key use case)

Multi-Agent Coordination Patterns

Message Passing

Agents communicate by sending structured messages. No agent reads another's internal state directly.

@dataclass
class AgentMessage:
  sender: str
  recipient: str
  content: dict
  message_type: str # "task" | "result" | "error" | "observation"
  correlation_id: str # links request to response

Shared State via Coordinator

Rather than a global shared object, a coordinator agent holds the shared state and exposes a controlled API for reading and writing. This preserves encapsulation while allowing coordination.

Common mistake — global shared state

Beginners often create a global dict that all agents read and write freely. This causes race conditions in async systems, makes testing impossible, and violates encapsulation. Always use a coordinator or a message bus to mediate access to shared state.
