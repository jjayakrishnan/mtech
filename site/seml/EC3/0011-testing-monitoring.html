ML Testing Pyramid

Analogy — Software testing pyramid

In software engineering, the testing pyramid has unit tests at the base (many, fast, cheap), integration tests in the middle, and end-to-end tests at the top (few, slow, expensive). ML systems have the same structure, but each layer tests something different — not just code logic, but data and model behaviour.

LayerWhat you testExamplesTools
Unit (base)Individual functions, data transforms, model componentsSchema validation, feature transform correctness, loss function calculationpytest, Great Expectations, Pandera
IntegrationPipeline stages working togetherTrain-eval loop, data loader + model forward pass, feature store → modelpytest, DVC, MLflow
System / E2E (top)Full system with real dataModel accuracy on held-out set, latency under load, fairness metricsEvidently, Whylogs, Prometheus

Data Testing (the unique ML layer)

Traditional software tests don't test data. ML systems must. Key data tests:

  • Schema tests — correct columns, dtypes, no unexpected nulls
  • Distribution tests — feature distributions match training expectations (no drift)
  • Range tests — values within expected min/max bounds
  • Relationship tests — correlations and business rules hold (e.g. end_date ≥ start_date)
Exam tip — data testing is not optional

A common exam question: "Why is testing harder for ML than traditional software?" The core answer: ML systems depend on data quality AND model behaviour, both of which change over time without any code change. A bug in ML can be invisible — accuracy degrades gradually rather than throwing an exception.

Data Drift & Concept Drift

Covariate shift (data drift)

\( P(X) \) changes — the input distribution shifts. The model was trained on customers aged 25–45; now serving customers aged 60+. The relationship \( P(Y|X) \) is still valid, but the inputs are out of distribution.

Concept drift

\( P(Y|X) \) changes — the relationship between inputs and outputs shifts. A fraud detection model trained pre-COVID might flag legitimate transactions that are now normal (remote work expenses, online shopping surges). The world changed; the model's "concept" of fraud is stale.

Exam trap — data drift vs concept drift

Data drift: inputs change → model may still be correct if the decision boundary holds. Concept drift: the correct decision itself changes → retraining required. You can have data drift without concept drift and vice versa. Always distinguish which is occurring.

Types of Concept Drift

TypeDescriptionExample
SuddenDistribution changes abruptlyNew competitor launches, policy change
GradualDistribution shifts slowly over timeUser demographics age over years
RecurringOld distribution re-appears (seasonal)Holiday shopping patterns
IncrementalDistribution shifts in small stepsProduct catalogue slowly expands

Drift Detection Methods

Kolmogorov-Smirnov (KS) Test

Compares two continuous distributions by measuring the maximum absolute difference between their CDFs:

\[ D_{KS} = \sup_x | F_{ref}(x) - F_{prod}(x) | \]

A large \( D_{KS} \) (and small p-value) indicates the distributions differ significantly. Rule of thumb: p-value < 0.05 → flag as potential drift.

Population Stability Index (PSI)

PSI measures how much a distribution has shifted relative to a reference:

\[ PSI = \sum_{i=1}^{k} (P_{prod,i} - P_{ref,i}) \cdot \ln\!\left(\frac{P_{prod,i}}{P_{ref,i}}\right) \]
PSI valueInterpretationAction
< 0.1Negligible changeNo action
0.1 – 0.2Moderate shiftInvestigate
> 0.2Significant driftRetrain model

ADWIN (ADaptive WINdowing)

ADWIN is an online drift detector that maintains a sliding window of observations. It automatically shrinks the window when it detects a change in the distribution, signalling concept drift. Unlike batch methods (KS, PSI), ADWIN works on streaming data in real time.

When to use which
  • KS test — when you have batch reference + current samples; good for continuous features
  • PSI — when you need a business-interpretable threshold; works for categorical and binned numerical
  • ADWIN — when data arrives as a stream and you need real-time drift alerts

Production Model Monitoring

Beyond drift, production models need monitoring across four dimensions:

DimensionWhat to monitorAlert threshold example
Data qualityNull rates, schema violations, out-of-range valuesNull rate > 5% in any feature
Data driftPSI > 0.2, KS p-value < 0.05 per featureAny feature PSI > 0.2
Model performanceAccuracy, F1, AUC on labelled samplesAUC drops > 3 points vs baseline
System healthLatency (p50, p95, p99), throughput, error ratep99 latency > 500ms
The delayed label problem

You can monitor data drift immediately (no labels needed). But monitoring model performance requires ground truth labels — which may arrive days or weeks after prediction (e.g. did the customer actually churn?). Design your monitoring pipeline to handle delayed labels: proxy metrics first, then true performance metrics when labels arrive.

Tools: Evidently AI & Whylogs

Evidently AI

Evidently generates interactive HTML reports and dashboards for ML model monitoring. Core reports:

  • DataDriftReport — KS test and distribution plots for each feature
  • TargetDriftReport — drift in the target variable
  • ClassificationReport — precision, recall, F1, confusion matrix
  • RegressionReport — MAE, RMSE, residual plots

Whylogs

Whylogs computes lightweight statistical profiles (sketches) of datasets. Instead of storing every row, it stores summary statistics that can detect drift:

  • Counts, mean, std, min, max per feature
  • Histograms and quantile sketches
  • String frequency for categorical features

Profiles are tiny (<1 MB for millions of rows), making them suitable for real-time streaming pipelines.

Analogy — Blood test vs full scan

Evidently runs a full diagnostic on a dataset batch — like a comprehensive medical scan. Whylogs takes a blood sample (statistical sketch) that is lightweight enough to do continuously. Use Evidently for scheduled deep dives; use Whylogs for continuous stream monitoring.

A/B Testing & Shadow Deployment

A/B Testing

Split traffic between two model versions (A = current champion, B = challenger). Measure business metrics (CTR, conversion rate, revenue) and statistical significance of the difference.

Key requirements for valid A/B test
  • Random assignment — users assigned to A or B at random (or stratified)
  • Sample size — calculated via power analysis before launching: \( n = \frac{2\sigma^2 (z_{\alpha/2} + z_\beta)^2}{\delta^2} \)
  • No peeking — don't stop early when the result looks good (inflates false positives)
  • Holdout — keep a control group to detect novelty effects

Shadow Deployment (Shadow Mode)

The new model receives production traffic and makes predictions, but its predictions are not served to users — only the current model's predictions are. The shadow model's outputs are logged and compared offline. This lets you evaluate the new model on real traffic without any user impact.

Shadow deployment workflow
  1. Deploy new model in shadow mode behind a feature flag
  2. Route all production requests to both current and shadow models
  3. Log shadow predictions; serve only current model's output
  4. Compare distributions offline: does the shadow model agree with current? Does it differ in expected ways?
  5. When confident, promote shadow to A/B test or full rollout
